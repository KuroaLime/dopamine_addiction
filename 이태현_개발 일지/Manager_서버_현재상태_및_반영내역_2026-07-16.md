# Manager 서버 현재 상태 및 최종 반영 내역

- 작성 시점: 2026-07-16
- 실제 프로젝트 기준: `X:\Project\Manager`
- 검증 스테이징: `work\prebattle_shop_20260715\build_project`
- 최종 묶음: `work\final_server_bundle_20260716`
- 중요: 이 문서는 코드로 확인된 사실, 자동 시험으로 확인된 사실, 실제 2PC 시험이 필요한 사항을 구분한다.

## 1. 결론

현재 수정본은 지금까지 확인한 주요 서버 결함을 소스 수준에서 함께 보완한 누적본이다.

1. IOCP의 접속 폭주, 인증 전 패킷 남용, 잘못된 패킷, 느린 클라이언트의 송신 큐 적체를 제한한다.
2. Dedi 프로세스 시작 실패, 비정상 종료, 방 중단, ACK 중복, 포트 재사용을 명시적인 수명주기로 처리한다.
3. 무거운 월드 로드가 끝나기 전에 전투 및 카드가 시작되지 않도록 서버 gate를 사용한다.
4. 최초 카드 20장은 일부만 생성된 상태로 게임을 시작하지 않으며, 전부 생성 및 필수 클라이언트 표시 ACK 이후에만 상점 단계로 간다.
5. 카드 소유권과 서버 카드 레코드를 원자적으로 맞추고, 사망 드롭 위치를 NavMesh와 검증된 지면 trace로 찾는다.
6. 재접속 시 티켓, 카드, 위치 복구의 경계 상태를 정리하고 서버 권위 위치를 다시 전송한다.
7. 클라이언트가 호출할 수 있는 주요 RPC에 phase 검증, 인자 검증, 호출 속도 제한을 추가한다.
8. `PreBattleShop`을 표시용 상태가 아니라 실제 서버 권한 단계로 완성한다.

다만 다음 세 가지는 코드 수정만으로 완료 판정을 내리면 안 된다.

- 월드 자체의 에셋 로드 시간은 gate로 숨기거나 동기화할 수 있을 뿐, 맵을 쪼개거나 에셋을 최적화하지 않는 한 물리적인 로드 비용이 사라지지 않는다.
- 최신 소스의 `ManagerServer`는 UHT까지 통과했지만 이 환경에서는 소스 엔진 970개 작업의 cold build가 시작되어 최종 링크까지 기다리지 않았다. 실제 `X:` 반영 후 소스 엔진으로 Dedi를 다시 빌드해야 한다.
- 서로 다른 두 컴퓨터에서 Summer 포함 20장 생성, 사망 카드 드롭, 재접속 및 위치 보정은 최종 바이너리로 다시 실험해야 한다.

## 2. 서버 구성과 책임 경계

### 2.1 IOCP 서버

IOCP 서버는 로그인과 로비, 방 생성, Dedi 프로세스 할당, Dedi 제어 채널, 포트와 프로세스 수명주기를 맡는다. 실제 월드 시뮬레이션과 카드 권한은 갖지 않는다.

### 2.2 Unreal Dedicated Server

Dedi는 매치 티켓 검증, 플레이어 입장, phase 진행, 월드 로딩 gate, 카드 생성 및 소유권, 플레이어 위치, 전투와 상점 RPC 권한을 맡는다. 게임 상태의 최종 권한은 Dedi에 있다.

### 2.3 Unreal Client

클라이언트는 스트리밍 완료와 카드 표시 완료를 서버에 알리고, 입력을 RPC로 요청하며, 서버에서 복제된 카드와 위치를 표시한다. 클라이언트가 보낸 위치나 카드 소유권을 진실로 간주하지 않는다.

## 3. IOCP 전송 및 접속 안정성

### 3.1 송신 락 경계

- 방/세션 전역 락을 잡은 채 소켓 송신을 시작하지 않도록 대상 세션을 먼저 수집한다.
- 각 세션의 송신 큐는 세션 단위로 보호한다.
- 느리거나 읽지 않는 클라이언트 때문에 송신 큐가 무한히 늘어나지 않도록 큐 상한을 둔다.
- 상한을 넘긴 세션은 서버 전체를 정체시키지 않고 해당 연결만 정리한다.

### 3.2 접속 및 방 상한

- 전체 연결 수 상한과 로컬 제어 연결 예약분을 둔다.
- 외부 접속 폭주가 Dedi 제어 연결 자리까지 소모하지 못하게 한다.
- 방 인원 상한을 적용하고 큰 방 목록 패킷도 프로토콜 최대 크기를 넘지 않는지 시험했다.

### 3.3 수신 패킷 방어

- 알려지지 않은 패킷 종류를 거부한다.
- 고정 크기 패킷은 정확한 길이를 요구한다.
- 인증 전 허용 패킷과 인증 후 허용 패킷을 구분한다.
- 초당 수신 패킷 수를 제한하고 과도한 연결을 해제한다.
- 인증하지 않은 채 유휴 상태인 연결을 정리한다.
- ID와 비밀번호는 엄격한 UTF-8로 해석하며 잘못된 바이트열을 거부한다.
- 클라이언트 인증 패킷은 문자열 글자 수가 아니라 실제 UTF-8 바이트 수를 기록한다.

### 3.4 남는 보안 한계

현재 보완은 패킷 경계와 서비스 안정성에 대한 것이다. 비밀번호 전송을 암호화하거나 안전한 password hash 기반 계정 저장소를 도입한 것은 아니다. 인터넷 공개 서비스 수준으로 운영하려면 TLS 또는 별도 보안 채널, salted password hash, 계정 잠금 및 감사 정책이 추가로 필요하다.

## 4. Dedi 방, 프로세스 및 포트 수명주기

### 4.1 시작과 중단 프로토콜

- IOCP가 Dedi를 시작한 뒤 준비 ACK를 기다린다.
- Dedi가 매치를 시작할 수 없으면 명시적인 abort를 보낸다.
- ACK가 중복되더라도 같은 매치를 두 번 전이하지 않도록 멱등 처리한다.
- 제어 메시지는 최근 처리 결과를 캐시하여 재전송 시 같은 결과를 돌려준다.

### 4.2 프로세스 회수

- Windows Job Object에 Dedi 자식 프로세스를 연결한다.
- IOCP 종료 시 남은 Dedi가 고아 프로세스로 남지 않도록 한다.
- 정상 종료 중인 프로세스와 즉시 재사용 가능한 프로세스를 구분한다.
- 비정상 종료와 매치 abort에서 방 상태를 회복하고 다음 방을 시작할 수 있게 한다.

### 4.3 포트 회수

- 사용 중, 반환 대기, 격리, 재사용 가능 상태를 구분한다.
- 프로세스 종료 직후 같은 포트를 성급하게 재할당하지 않는다.
- 실제 바인딩 가능 여부를 확인한 뒤 포트를 반환한다.
- 실패 포트는 quarantine 후 재검사한다.

## 5. 무거운 월드 로딩과 게임 시작 gate

### 5.1 기존 문제

고정 15초, 120초, 150초 또는 300초를 기다리는 방식은 맵이 빨리 로드되면 불필요하게 늦고, 느리게 로드되면 여전히 너무 이르다. 특히 다른 컴퓨터의 클라이언트는 에디터와 같은 컴퓨터에서 실행한 클라이언트보다 로드와 복제가 늦을 수 있다.

### 5.2 현재 방식

- Dedi가 메인 월드 준비 상태를 관리한다.
- 각 필수 클라이언트가 메인 월드 스트리밍 완료를 ACK한다.
- 서버가 최초 카드 묶음 생성 완료를 확인한다.
- 각 필수 클라이언트가 카드 묶음 표시 완료를 ACK한다.
- 위 조건을 모두 충족해야 `PreBattleShop`으로 이동한다.
- 일부 클라이언트만 준비됐다는 이유로 부분 시작하지 않는다.
- 진행이 전혀 없는 상태에 대한 장시간 보호 timeout은 두되, 정상 로딩을 임의의 짧은 고정 시간으로 자르지 않는다.

### 5.3 이 방식이 해결하는 것과 해결하지 않는 것

해결하는 것:

- 느린 원격 클라이언트가 로딩 중인데 서버가 카드를 먼저 생성하거나 전투를 시작하는 순서 오류
- 서버에는 카드가 있지만 클라이언트가 월드/카드를 아직 표시하지 못한 상태에서 게임이 진행되는 오류
- 일부 카드만 생성됐는데 정상 게임처럼 진행되는 오류

해결하지 않는 것:

- 큰 텍스처, 메시, 셰이더, 액터 수, 충돌 및 NavMesh 때문에 발생하는 순수 에셋 로드 시간
- 클라이언트 PC 사양 차이 자체

맵을 쪼갤 수 없다면 에셋 크기, LOD/Nanite, 텍스처 스트리밍, 충돌 복잡도, 불필요한 BeginPlay 작업, 셰이더 준비와 액터 수를 프로파일링해야 실제 로드 시간이 줄어든다.

## 6. 최초 카드 20장 생성

### 6.1 원자적 생성

- 계획한 카드 수, 위치 탐색 성공 수, 실제 spawn 성공 수를 구분한다.
- 한 장이라도 필수 생성에 실패하면 성공으로 보고 다음 phase를 시작하지 않는다.
- 실패한 부분 생성 묶음은 정리한 뒤 재시도한다.
- 모든 카드가 서버에서 생성되고 필수 클라이언트가 표시 완료를 ACK해야 gate가 열린다.

### 6.2 Summer 섬

Summer의 NavMesh가 정상 위치를 주지 못하는 경우를 위해 지면 trace fallback을 유지한다. fallback은 단순한 임의 좌표가 아니다.

- 여러 높이에서 수직 trace로 실제 지면을 찾는다.
- Pawn 충돌은 무시한다.
- 경사 한계를 검사한다.
- 허용 반경 밖 좌표를 거부한다.
- no-drop 영역을 거부한다.
- 기존 카드와 최소 거리를 검사한다.
- 카드 배치 충돌과 머리 위 여유 공간을 검사한다.

NavMesh를 무조건 크게 만드는 것만으로 Summer 문제를 확정 해결할 수는 없다. NavData가 실제로 생성됐는지, bounds가 섬 지형을 덮는지, 지형 collision이 navigation에 기여하는지, agent 설정이 일치하는지를 함께 확인해야 한다.

## 7. 카드 소유권, 버리기 및 사망 드롭

### 7.1 단일 서버 레코드

카드에는 서버 레코드가 있으며 월드 드롭, 플레이어 소유, 버려짐 상태를 구분한다. 이번 수정으로 `Discarded` 상태를 명시적으로 추가했다.

### 7.2 일반 버리기

클라이언트가 카드 ID만 보냈다고 바로 소유 목록에서 제거하지 않는다.

1. PlayerState가 해당 카드를 소유하는지 검사한다.
2. 서버 카드 레코드의 소유자, 카드 ID, 상태가 같은지 검사한다.
3. 소유 목록 제거가 성공한 뒤 레코드를 `Discarded`로 전이한다.
4. 어느 단계든 불일치하면 요청을 거부하고 상태를 유지한다.

### 7.3 사망 드롭

- BattleRoyale에서만 사망 카드 드롭을 실행한다.
- PlayerState 소유 정보와 서버 카드 레코드가 일치하는 카드만 처리한다.
- NavMesh 탐색을 우선 사용한다.
- NavMesh 실패 시 검증된 ground trace fallback을 사용한다.
- 안전 위치를 찾지 못하면 임의의 방사형 좌표에 강제로 생성하지 않는다.
- 위치 실패 시 카드 소유 상태를 먼저 지우지 않고 `DeathDropDeferred`로 남긴다.
- 월드 액터 spawn과 소유 목록 변경, 레코드 상태 전이를 실패 시 되돌릴 수 있는 순서로 처리한다.
- 남아 있던 stale drop actor 참조를 정리한다.

이 변경은 잘못된 위치에 카드를 떨어뜨리는 것보다 서버 상태 보존을 우선한다. 따라서 극단적인 지형에서 안전한 위치가 하나도 없으면 카드가 즉시 보이지 않을 수 있고, 그때는 실패 로그로 위치 조건을 조사해야 한다.

### 7.4 라운드 경계

연결이 끊긴 플레이어의 snapshot에 남은 이전 라운드 카드가 다음 라운드 또는 재접속에서 되살아나지 않도록 전투 전이, 게임 종료, 매치 abort에서 분리된 카드 레코드를 정리한다.

## 8. 재접속과 서버 권위 위치

### 8.1 티켓 예약 단계

기존에는 `PreLogin`에서 티켓을 바로 활성 상태로 바꾸면 `InitNewPlayer` 전에 연결이 끊긴 경우 티켓이 붙잡힐 수 있었다.

- `PreLogin`에서는 pending reservation을 만든다.
- `InitNewPlayer`가 실제 컨트롤러 생성에 성공한 뒤 active로 전환한다.
- 초기화 실패 또는 reservation timeout에서 pending을 제거한다.
- 같은 티켓의 중복 active/pending 입장을 거부한다.

### 8.2 위치 복구

- 재접속 snapshot의 transform을 서버가 적용한다.
- Pawn 준비가 늦으면 일정 시간 반복 시도한다.
- 복구 성공 후 서버 권위 위치를 클라이언트에 다시 보낸다.
- 제한 시간 안에 복구하지 못하면 현재 서버 위치를 최종값으로 보내고 오래된 snapshot을 제거한다.
- 위치 복구 실패 때문에 유효한 티켓이나 카드 상태 전체를 함께 삭제하지 않는다.

이것은 서버 측 복구 정합성을 보완한 것이다. 네트워크가 끊긴 클라이언트가 자동으로 Dedi에 다시 접속하는 UI/재시도 UX 전체를 새로 구현한 것은 아니다.

## 9. RPC 권한과 호출 속도 제한

### 9.1 PlayerController RPC

- 클라이언트의 임의 `SwitchMode`와 `SetUITimer` 호출은 validation에서 거부한다.
- `PushMode`는 Shop만 허용하고 실제 phase 및 상점 가능 상태를 다시 검사한다.
- 랜덤 강화와 고정 강화 인덱스 범위를 검사한다.
- 카드 표시 ACK 수에 상한을 둔다.
- 스트림 ACK, 카드 ACK, 상점 push/pop, 강화 선택 요청에 호출 속도 제한을 둔다.
- 섯다 베팅 enum 범위를 검사한다.
- 카드 버리기는 CardGameService의 서버 권한 경로만 사용한다.

### 9.2 AbilitySystem RPC

- ability activation, cancel, gameplay event에 각각 고정 구간 호출 상한을 둔다.
- prediction key가 유효한 양수인지 검사한다.
- cancel tag 개수를 제한한다.
- gameplay event는 정확한 trigger tag와 실제 부여된 trigger를 확인한다.
- 제한 경고 로그도 cooldown을 둬 로그 폭주를 막는다.

## 10. PreBattleShop

- 카드 gate 완료 후 바로 BattleRoyale을 시작하지 않고 PreBattleShop을 시작한다.
- 이 단계에서 Pawn은 보이지만 이동과 전투는 비활성화된다.
- 서버의 `bShopAvailable`, 실제 phase, 게임 시작 상태가 모두 맞아야 상점 RPC를 승인한다.
- 종료 시 상점 가능 상태를 먼저 내리고 열린 상점 모드와 미선택 랜덤 후보를 서버가 정리한다.
- 그 뒤 timed BattleRoyale과 이동/전투를 활성화한다.
- PreBattleShop 중 재접속한 클라이언트도 메인 월드 상태를 동기화한다.
- 발사 서버 처리는 실제 BattleRoyale 및 카드 gate 완료 상태에서만 허용한다.

## 11. 로그 정책

정상 프레임이나 반복 성공 경로에 매번 로그를 추가하지 않고 상태 전이, 실패 원인, 집계 중심으로 유지한다. 로그 자체는 문자열 포맷, 동기 출력, 디스크 I/O 때문에 비용이 있으며 특히 매 프레임 또는 패킷마다 Warning/Error를 찍으면 서버를 느리게 할 수 있다.

중요 확인 지점:

- Dedi 시작, 준비, abort, 종료, 포트 quarantine/reclaim
- `CardSpawnSummary`의 Planned, LocationFound, Spawned
- gate의 필수/준비 클라이언트 수와 카드 수
- Summer/NavMesh/fallback 위치 실패 카운터
- `DeathDropDeferred` 및 카드 레코드 불일치
- reconnect transform retry/success/fallback
- rate limit 또는 잘못된 RPC 거부

## 14. 최종 반영 방식

`Apply-ManagerServerBundle.ps1`은 다음 순서로 동작한다.

1. Unreal, Manager, ManagerServer, IOCP 프로세스가 모두 꺼졌는지 검사한다.
2. 묶음 baseline/payload 26개 파일의 SHA-256을 검사한다.
3. 현재 `X:` 26개 파일이 묶음을 만든 시점의 baseline과 같은지 검사한다.
4. `Saved\CodexBackups` 아래에 현재 파일을 전부 백업한다.
5. 22개 소스와 검증된 Editor/IOCP 바이너리 4개를 복사한다.
6. 복사 후 payload SHA-256과 다시 비교한다.
7. 상세 보고서와 통합 일지를 `X:\이태현_개발 일지`에 복사한다.
8. 어느 파일에서든 실패하면 이미 복사한 프로젝트 파일을 백업본으로 되돌린다.

기본 실행은 `X:`가 중간에 바뀌면 중단한다. `-Force`는 그 변경을 정말 덮어쓸 때만 사용한다.

### 14.1 배포 도구 자체 검증

실제 `X:` 기준선 26개 파일로 별도 가짜 프로젝트를 만든 뒤 다음 순서를 자동 시험했다.

1. baseline SHA-256 검사
2. 26개 파일 백업
3. payload 적용
4. 적용 후 payload SHA-256 전부 일치
5. 보고서 및 반영 기록 생성
6. 백업 복원
7. 복원 후 baseline SHA-256 전부 일치

추가로 한 대상 파일을 의도적으로 payload 버전으로 바꾼 뒤 다시 실행했다. 스크립트는 `X: changed after this bundle was prepared` 오류와 exit code 1로 복사 전에 중단했고, 보고서 폴더도 만들지 않았다. 따라서 기본 실행은 묶음 작성 이후의 사용자 변경을 자동으로 덮어쓰지 않는다.

## 1. 현재 코드의 큰 구조

### 1.1 전체 흐름

현재 프로젝트는 크게 다음 흐름으로 동작한다.

1. 클라이언트가 IOCP 서버에 접속한다.
2. IOCP 서버가 로그인, 방 생성, 방 입장, 준비 상태, 게임 시작 요청을 처리한다.
3. 방장이 게임 시작을 누르면 IOCP가 Dedi 서버를 실행한다.
4. IOCP는 일정 시간 대기 후 클라이언트들에게 `S2C_GAME_START` 패킷을 보낸다.
5. 클라이언트는 `S2C_GAME_START`를 받고 `ClientTravel`로 Dedi 서버에 접속한다.
6. Dedi 서버의 `MainGameMode`가 인게임 페이즈를 진행한다.
7. TPS 페이즈에서 카드 월드 드랍이 생성된다.
8. 카드 페이즈에서 섯다 카드 처리, 베팅, 결과 정산이 진행된다.
9. 매치 종료 시 Dedi가 IOCP에 매치 종료 패킷을 보낸다.

현재 가장 큰 문제는 3번부터 7번까지의 준비 상태 공유가 시간 추측에 의존한다는 점이다.

## 3. 현재 가장 큰 서버/Dedi 문제

### 3.1 IOCP가 Dedi 준비 상태를 모른다

확인 위치:

- `X:\Project\Manager\Server\LobbyService.cpp:64`
- `X:\Project\Manager\Server\LobbyService.cpp:1389`
- `X:\Project\Manager\Server\Protocol_D.h:34`

현재 코드:

- `DEDI_GAME_START_DELAY_SECONDS = 15`
- Dedi 서버 실행 후 `std::this_thread::sleep_for(std::chrono::seconds(DEDI_GAME_START_DELAY_SECONDS))`
- 시간이 지나면 클라이언트에게 `S2C_GAME_START` 전송
- `D2L_SERVER_READY_NOTIFY` 같은 준비 완료 패킷은 현재 없다.

문제:

- Dedi가 실제로 listen 가능 상태인지 IOCP가 확인하지 않는다.
- 맵이 무거우면 15초는 부족하다.
- 150초, 300초로 늘려도 본질은 해결되지 않는다. 단지 문제 발생 시점을 늦출 뿐이다.
- 빠른 PC, 느린 PC, 에디터 실행, 패키징 실행, 원격 PC 환경마다 필요한 시간이 달라진다.

필요한 수정:

1. 서버 프로토콜에 `D2L_SERVER_READY_NOTIFY = 301` 추가.
2. 클라이언트 프로토콜 쪽에도 동일한 enum 값 추가.
3. Dedi 서버가 `RoomId`, `Port`, 가능하면 `ServerToken`을 포함해서 IOCP에 ready notify 전송.
4. IOCP는 고정 sleep 대신 roomId 기준 pending room을 보관한다.
5. ready notify를 받은 뒤에만 `S2C_GAME_START`를 클라이언트들에게 보낸다.
6. timeout은 "강제 GAME_START"가 아니라 오류 로그와 room rollback 또는 retry 용도로만 사용한다.

## 4. 카드 월드 드랍 문제

### 4.1 `NotEnoughDropZones`면 현재는 섬 카드 스폰 전체가 중단된다

확인 위치:

- `X:\Project\Manager\Source\Manager\Game\InGame\Card\CardGameService.cpp:1206`
- `X:\Project\Manager\Source\Manager\Game\InGame\Card\CardGameService.cpp:1209`

현재 코드 의미:

- 찾은 드랍존 수가 카드 그룹 수보다 적으면 `NotEnoughDropZones` 로그를 남긴다.
- 결과는 `AbortIslandCardSpawn`.

문제:

- 드랍존을 일부라도 찾았어도 전체 섬 카드 스폰이 중단된다.
- 여름 섬에서 드랍존 인식이 실패하면 카드가 아예 생성되지 않는다.
- 사용자가 말한 "Not Enough Drop Zones" 기억과 현재 코드가 맞다.

1. 드랍존이 부족하면 전체 중단이 아니라 fallback 모드로 전환.
2. 발견된 zone에는 정상 배치.
3. 부족한 zone은 season island bounds 또는 tagged actor bounds에서 보조 zone 생성.
4. 그것도 실패하면 서버 기준 ground trace fallback으로 안전 위치 산출.
5. 실패 로그는 유지하되, 가능한 카드는 최대한 스폰되게 한다.

## 5. 위치 동기화 문제

### 5.1 현재 위치 문제의 중심은 서버 권위 이전의 준비 상태 부족

현재 코드에서 위치 동기화는 단순히 "캐릭터 movement replication이 없음" 하나로 볼 문제가 아니다.

직접적인 구조 문제:

- 서버가 플레이어의 레벨 로딩 완료를 모른다.
- 서버가 TPS/Card stage 전환 완료를 모른다.
- 서버가 카드 스폰과 플레이어 이동을 페이즈 전환 직후 바로 진행한다.
- 클라이언트별 로딩 시간이 다르면 같은 서버 위치라도 클라에서 보이는 상태가 어긋날 수 있다.

필요한 수정:

1. 페이즈별 서버 권위 기준 anchor를 정한다.
2. 클라이언트 로딩 완료 ACK 이후 서버가 위치를 확정한다.
3. 서버가 `SetActorLocation` 또는 teleport를 수행한다.
4. 이후 클라이언트는 서버 위치를 따라가도록 한다.
5. 위치 보정은 로딩 완료 전이 아니라 로딩 완료 후에 실행한다.

## 13. 바로 다음 작업 제안

가장 먼저 해야 할 것은 `Dedi ready notify`다.

이유:

- 맵 로딩이 오래 걸리는 문제를 sleep으로 해결하려고 하면 계속 실패한다.
- Dedi가 실제 준비되기 전에 클라이언트를 보내면 이후 모든 문제가 연쇄로 생긴다.
- 이 작업이 끝나야 클라이언트 로딩 ACK와 카드 스폰 gate도 정확히 붙일 수 있다.

그 다음은 `클라이언트 로딩 완료 ACK`다.

이유:

- Dedi ready는 "서버가 접속 받을 준비"까지만 보장한다.
- 카드 스폰과 위치 보정은 "각 클라가 stage를 실제로 로딩 완료"한 뒤 해야 한다.

세 번째는 `카드 스폰 gate`다.

이유:

- 현재 코드에서 카드 스폰은 TPS 페이즈 시작 직후 실행된다.
- 이 위치를 gate 뒤로 옮겨야 여름 섬, 원격 PC, 느린 로딩 환경에서 안정화된다.

1. Dedi ready notify.

3. 카드 스폰 gate.
4. 카드 위치 fallback.

6. IOCP 안정성.

이 순서가 현재 코드 기준 가장 안전하다.

### 16.1 해결 2: `NotEnoughDropZones` 복구 처리

기존 문제:

- `SpawnRoundCardBundleForBattleRoyale()`에서 `IslandDropZones.Num() < IslandCardGroups.Num()`이면 바로 return했다.
- 이 상태에서는 한 섬이라도 드랍존이 부족하면 해당 라운드의 월드 카드 드랍이 통째로 생성되지 않았다.
- 특히 맵/섬 구성 차이, 드랍존 액터 인식 실패, Bounds 계산 실패가 있으면 `NotEnoughDropZones` 계열 로그 이후 카드가 안 보이는 현상으로 이어질 수 있었다.

반영 내용:

1. 드랍존 수가 카드 그룹 수보다 적어도 즉시 abort하지 않는다.
2. 드랍존이 1개 이상이면 부족한 그룹은 기존 드랍존을 modulo 방식으로 재사용한다.
3. 드랍존이 0개면 `CardBundleDropCenter`, `CardBundleDropExtent`, `CardIslandGroundTraceHalfHeight` 기반의 가상 fallback zone을 생성한다.
4. fallback zone의 `IslandKey`는 `BundleFallback`, `Source`는 `GeneratedBundleBounds`로 남긴다.
5. 같은 드랍존을 여러 카드 그룹이 공유할 수 있으므로 기존 위치 목록을 `TMap<int32, TArray<FVector>> ExistingLocationsByZoneIndex`로 zone index별 관리한다.

의미:

- 드랍존 인식이 완벽하지 않아도 카드 월드 드랍 전체가 0개가 되는 상황을 줄였다.
- 드랍존이 완전히 없을 때도 기존 번들 범위 설정을 이용해 최소한의 월드 드랍을 시도한다.
- 로그에서 `DropZoneRecover`, `GeneratedBundleBounds`, `ZoneIndex`를 보면 복구 경로를 탔는지 확인할 수 있다.

주의:

- 이 수정은 카드 드랍을 "안 하는 문제"를 막는 1차 복구다.
- 맵 자체 bounds가 잘못되어 있거나 fallback 중심/범위가 섬 밖이면 카드가 이상한 위치에 떨어질 수 있다.
- 따라서 멀티 테스트에서 카드가 보이긴 하지만 위치가 어긋나면 다음 단계는 `CardBundleDropCenter/Extent`, ground trace 결과, island zone actor 배치 값을 다시 봐야 한다.

### 16.2 해결 4: Dedi ticket 완전 검증

기존 문제:

- Dedi `PreLogin()`은 ticket이 비었는지, 숫자인지, 0보다 큰지만 확인했다.
- IOCP는 `S2C_GAME_START`의 ticket 값으로 session id를 그대로 보냈다.
- 따라서 "이 ticket이 실제로 이 방 시작 때 IOCP가 발급한 값인가", "이미 사용한 ticket인가"를 검증하지 못했다.

반영 내용:

1. `LobbyService::Room`에 `handoverTickets`를 추가했다.
   - 구조: `Session ID -> one-time Dedi ticket`
2. 방 시작 요청이 정상 조건을 통과하고 Dedi 실행 직전에 멤버별 랜덤 ticket을 생성한다.
3. `LaunchDedicatedServer()`에 `allowedTickets` 인자를 추가했다.
4. Dedi 실행 map option에 `?Tickets=티켓1,티켓2,...`를 붙인다.
   - 예: `...?RoomId=3?RequiredPlayers=2?Tickets=123456789,987654321`
5. `SendGameStartForRoom_Unsafe()`는 더 이상 session id를 ticket으로 보내지 않는다.
6. `SendGameStartForRoom_Unsafe()`는 해당 멤버의 `handoverTickets[mSid]`를 찾아 `S2C_GAME_START` ticket으로 보낸다.
7. Dedi `AMainGameMode::InitGame()`은 `Tickets` option을 파싱해서 `AllowedDediTickets`에 저장한다.
8. Dedi `AMainGameMode::PreLogin()`은 다음을 모두 검사한다.
   - ticket 없음: `MissingTicket`
   - ticket 형식 오류/0 이하: `InvalidTicket`
   - Dedi가 허용 ticket 목록을 못 받은 상태: `MissingTicketList`
   - 허용 목록에 없는 ticket: `UnknownTicket`
   - 이미 사용한 ticket 재사용: `ReusedTicket`
9. 정상 통과한 ticket은 `UsedDediTickets`에 추가하여 1회성으로 처리한다.
10. Dedi 실행 실패 rollback, 매치 종료, 방 이탈 경로에서 `handoverTickets`를 정리한다.

의미:

- 이제 Dedi는 단순히 숫자 ticket만 받는 것이 아니라, IOCP가 해당 방 시작 때 넘겨준 ticket 목록과 대조한다.
- 클라가 임의 숫자 ticket으로 Dedi에 직접 접속하는 흐름은 `UnknownTicket`으로 거부된다.
- 같은 ticket으로 두 번 들어오려는 흐름은 `ReusedTicket`으로 거부된다.

주의:

- 현재 ticket 목록은 Dedi 실행 command line/map option으로 전달된다. 로컬 개발/시험 기준으로는 충분하지만, 운영 보안까지 보려면 ticket 만료 시간, room id와 ticket의 서버 내부 저장소 대조, Dedi ready/match notify 인증까지 별도 설계가 필요하다.
- `InitGame` 로그에는 기존처럼 `Options` 전체가 찍히므로 `Tickets=` 값도 로그에 노출될 수 있다. 로그 정리 단계에서 ticket 원문 마스킹을 고려해야 한다.

### 16.3 해결 5: IOCP send/context/port pool 안정화

기존 문제:

- `SendPacket()`에서 최초 `WSASend`가 즉시 실패하면 실패한 패킷이 send queue에 남고 `sendInFlight` 상태만 내려갈 수 있었다.
- send completion 이후 다음 패킷 `WSASend`가 실패하는 경로에서 queue/ref 정리가 불명확했다.
- 여러 종료 경로가 `closesocket(client->sock)`을 직접 호출해 같은 socket close가 중복될 여지가 있었다.
- `ReleaseIO()`도 delete 직전에 다시 `closesocket(c->sock)`을 호출했다.
- `FreePort()`는 같은 Dedi port가 중복 반환되는지 검사하지 않았다.

반영 내용:

1. `CloseClientSocketOnce(ClientContext*)`를 추가했다.
   - `closeLock`으로 보호한다.
   - socket을 `INVALID_SOCKET`으로 먼저 바꾼 뒤 `shutdown/close`한다.
2. `MarkClientClosing(ClientContext*, reason)`을 추가했다.
   - `closing.exchange(true)` 최초 1회에만 `g_lobby.OnClientDisconnected()`를 호출한다.
   - 이후 socket close는 `CloseClientSocketOnce()`로 통일한다.
3. `ReleaseIO()`는 delete 직전에 직접 `closesocket`하지 않고 `CloseClientSocketOnce()`만 호출한다.
4. `SendPacket()` 시작 시 이미 closing인 context에는 더 이상 send를 쌓지 않는다.
5. 최초 `WSASend` 즉시 실패 시:
   - send queue clear
   - `sendInFlight=false`
   - `MarkClientClosing(..., "WSASendStartFailed")`
   - send ref `ReleaseIO`
   - send context delete
6. 부분 송신 재시도 실패 시:
   - send queue clear
   - `sendInFlight=false`
   - `MarkClientClosing(..., "WSASendPartialRetryFailed")`
   - send ref `ReleaseIO`
7. 다음 패킷 송신 실패 시:
   - send queue clear
   - `sendInFlight=false`
   - `MarkClientClosing(..., "WSASendNextFailed")`
   - send ref `ReleaseIO`
8. recv EOF, IOCP completion 실패, invalid packet size, recv repost 실패 경로도 `MarkClientClosing()`로 통일했다.
9. 최초 accept 직후 `WSARecv` 실패는 아직 로비 등록 전이므로 `OnClientDisconnected()`를 부르지 않고 `CloseClientSocketOnce()`와 `ReleaseIO()`만 수행한다.
10. `FreePort()`는 이미 free pool에 들어 있는 port면 다시 push하지 않고 `[DEDI] FreePort skipped duplicate ...` 로그만 남긴다.

의미:

- send 실패 후 실패 패킷/상태가 큐에 남아 다음 송신을 오염시키는 위험을 줄였다.
- 같은 client socket이 여러 완료 경로에서 중복 close되는 위험을 줄였다.
- Dedi port가 중복 반환되어 같은 port를 여러 방이 배정받는 위험을 줄였다.

주의:

- 이번 수정은 send 실패/close/중복 port 반환의 안정화다.
- 아직 "IN_GAME 방이 비었을 때 Dedi process를 어떻게 회수할 것인가", "Dedi가 비정상 종료됐을 때 IOCP가 port를 언제 회수할 것인가"는 별도 문제로 남아 있다.
- `ServerMain.cpp`의 C4819 인코딩 경고는 기존처럼 남아 있다.

### 17.1 이번 수정의 핵심 결론

기존 구조의 가장 큰 문제는 Dedi 서버가 TPS 월드를 완전히 로드한 클라이언트 상태와 무관하게 BattleRoyale phase 시작 직후 카드를 생성한다는 점이었다. 내 컴퓨터에서 서버/클라를 같이 켠 경우에는 로딩 타이밍이 비슷해서 우연히 보일 수 있지만, 다른 컴퓨터 클라이언트가 느리게 로드하면 서버는 이미 카드 위치를 계산하고 스폰했는데 클라는 아직 해당 스트리밍 레벨/월드 상태가 준비되지 않은 상태가 될 수 있다.

이번 수정 후 구조는 다음 순서가 된다.

1. Dedi가 TPS phase 진입을 시작한다.
2. `UTPSPhaseStrategy::OnPhaseStart()`는 더 이상 즉시 `SpawnRoundCardBundleForBattleRoyale()`를 호출하지 않는다.
3. 대신 `AMainGameMode::RequestBattleRoyaleCardSpawnAfterStreamReady()`를 호출해서 카드 스폰을 pending 상태로 둔다.
4. 각 클라이언트가 `ServerNotifyStreamLevelLoaded()`를 통해 `TPS_Game_Stage` 로딩 완료 ACK를 보낸다.
5. 서버는 `ClientLoadedStreamLevels`를 확인해서 필요한 클라이언트가 `TPS_Game_Stage` 로딩을 끝냈는지 검사한다.
6. 조건이 안 맞으면 `BattleRoyaleCardSpawnGateRetryInterval` 주기로 계속 재시도한다.
7. 조건이 맞으면 그때 서버가 카드 번들을 생성한다.
8. 카드 번들 생성이 끝난 직후에만 BattleRoyale 제한 시간 타이머를 시작한다.

이 방식의 의미:

- 로딩이 15초, 150초, 300초처럼 길어져도 고정 fallback 시간 때문에 먼저 카드가 생성되는 문제를 피한다.
- 맵이 늦게 뜨는 클라이언트 때문에 서버 카드 드랍이 너무 빨리 진행되는 문제를 줄인다.
- BattleRoyale 타이머가 로딩 중에 먼저 소모되어 카드가 스폰되기 전에 `TransitionToCard`로 넘어가는 문제를 막는다.

### 17.4 BattleRoyale 타이머 시작 위치 변경

이전에는 `StartBattleRoyalePhase()` 안에서 곧바로 `StartTimedServerPhase(EDediServerPhase::BattleRoyale, GetBattleRoyaleDuration())`를 호출했다.

이 구조의 문제:

- 맵 로딩이 BattleRoyale 제한 시간보다 길면, 카드가 생성되기 전에 BattleRoyale timeout이 먼저 올 수 있다.
- 그 경우 `StartTransitionToCardPhase()`가 호출되고 `ClearBattleRoyaleCardSpawnGate()`가 실행되어 pending 카드 스폰이 취소된다.
- 결과적으로 "로딩이 너무 긴 맵에서 카드가 안 보임" 문제가 다시 발생할 수 있다.

수정 후:

- `StartBattleRoyalePhase()`는 `BeginPhase(EGamePhase::TPS)` 이후 `CurrentServerPhase`를 `BattleRoyale`로 준비 상태만 만든다.
- `RemainingPhaseSeconds`는 0으로 두고 UI 시간도 0으로 맞춘다.
- `TrySpawnBattleRoyaleCardsWhenStreamReady()`가 실제 카드 스폰을 끝낸 뒤 `StartTimedServerPhase(EDediServerPhase::BattleRoyale, GetBattleRoyaleDuration())`를 호출한다.

의미:

- BattleRoyale 제한 시간은 "클라 로딩 ACK 완료 + 서버 카드 스폰 완료" 이후부터 돈다.
- 무거운 메인 게임 월드 때문에 로딩이 길어져도 카드 스폰 gate가 먼저 취소되지 않는다.

### 17.5 TPSPhaseStrategy 즉시 스폰 제거

`UTPSPhaseStrategy::OnPhaseStart()`에서 기존 즉시 스폰 호출을 제거했다.

이전:

### 17.6 CardPlacementService 위치 후보 보강

Summer 섬처럼 카드가 안 보였던 문제는 드랍존 방식이 아니라 현재 코드 기준으로도 "서버가 계산한 카드 위치 후보가 전부 실패"할 수 있는 구조와 연결된다. 특히 다음 케이스가 위험했다.

- `NotEnoughDropZones`
- `NoNavAnchor`
- `NoNavSystem`
- Nav 후보는 잡혔지만 Z sanity, bounds, overlap, overhead, no-drop 검증에서 모두 탈락

이번 반영 상태:

- 드랍존 수가 카드 그룹 수보다 적어도 전체 abort하지 않고 zone을 재사용한다.
- 드랍존이 0개면 `GeneratedBundleBounds` 기반 fallback zone을 만든다.
- `NavAnchors.Num() == 0`이어도 즉시 실패하지 않고 `GroundTraceFallback`으로 내려간다.
- `UNavigationSystemV1::GetCurrent(World)`가 null이어도 즉시 실패하지 않고 `GroundTraceFallback`으로 내려간다.
- Nav 기준 Z가 없을 때는 ground trace hit 지점의 Z를 기준으로 sanity 검사를 수행한다.

로그 기준으로 확인해야 할 흐름:

```text
[DS] Card DropNoNavAnchor ... Result=TryGroundTraceFallback
[DS] Card DropNoNavSystem ... Result=TryGroundTraceFallback
[DS] Card DropInstance ... PickSource=GroundTraceFallback ...
```

아직 실제 플레이에서 다시 봐야 하는 것:

- Summer 섬의 실제 collision/trace channel이 ground trace에 잡히는지
- Summer 섬의 bounds가 서버 dedicated 환경에서도 클라와 같은 위치/크기로 계산되는지
- `CardNoDropZoneTag`가 의도치 않게 전체 섬을 막고 있지 않은지
- Overhead clearance가 나무/지형 오브젝트 때문에 전부 reject하지 않는지

### 18.3 Dedi 프로세스/포트 회수 구조 변경

기존 구조:

- `LaunchDedicatedServer()`가 `CreateProcessA()` 성공 후 `pi.hProcess`를 바로 `CloseHandle()` 했다.

반영 구조:

- `Room`에 다음 필드 추가:

```cpp
HANDLE dedicatedProcessHandle = NULL;
DWORD dedicatedProcessId = 0;
```

- `LaunchDedicatedServer()` 시그니처 변경:

```cpp
bool LaunchDedicatedServer(
    uint16_t port,
    uint32_t roomId,
    uint16_t requiredPlayers,
    const std::string& allowedTickets,
    HANDLE& outProcessHandle,
    DWORD& outProcessId);
```

- Dedi 실행 성공 시:
  - thread handle은 닫음.
  - process handle은 닫지 않고 room에 넘김.
  - room이 launch 중간에 삭제되었으면 방금 실행한 Dedi를 즉시 `TerminateProcess()` 후 handle close.

### 18.4 회수 함수

추가 함수:

```cpp
void CleanupDedicatedServerForRoom_Unsafe(Room& room, const char* reason, bool terminateProcess);
void SweepDedicatedServerProcesses();
```

`CleanupDedicatedServerForRoom_Unsafe()` 역할:

- room의 `dedicatedPort`를 0으로 초기화.
- port를 free pool로 반환.
- `gameStartSent`를 false로 초기화.
- handover ticket 목록 제거.
- process handle이 있으면 상태 확인.
- 아직 살아 있고 `terminateProcess=true`이면 `TerminateProcess()` 호출.
- 마지막에 process handle close.

`SweepDedicatedServerProcesses()` 역할:

- 현재 room들이 들고 있는 Dedi process handle을 검사.
- Dedi process가 이미 종료되어 있으면:
  - 오류 로그 출력.
  - port 반환.
  - handle close.
  - room을 `WAITING`으로 되돌림.
  - ready 상태를 host만 true로 재초기화.
  - room list/member list broadcast.
- process handle 조회 자체가 실패해도 무한 잔존하지 않도록 cleanup 처리.

스윕 호출 지점:

- `OnClientAccepted()`
- `OnClientDisconnected()`
- `OnPacket()`

즉, 별도 background thread는 아직 없지만 IOCP에 새 이벤트가 들어올 때 죽은 Dedi room/port를 회수한다.

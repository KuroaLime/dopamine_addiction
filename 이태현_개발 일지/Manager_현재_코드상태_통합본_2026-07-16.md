## 1. 현재 코드의 큰 구조

### 1.1 전체 흐름

현재 프로젝트는 크게 다음 흐름으로 동작한다.

1. 클라이언트가 IOCP 서버에 접속한다.
2. IOCP 서버가 로그인, 방 생성, 방 입장, 준비 상태, 게임 시작 요청을 처리한다.
3. 방장이 게임 시작을 누르면 IOCP가 Dedi 서버를 실행한다.
4. IOCP는 일정 시간 대기 후 클라이언트들에게 `S2C_GAME_START` 패킷을 보낸다.
5. 클라이언트는 `S2C_GAME_START`를 받고 `ClientTravel`로 Dedi 서버에 접속한다.
6. Dedi 서버의 `MainGameMode`가 인게임 페이즈를 진행한다.
7. TPS 페이즈에서 카드 월드 드랍이 생성된다.
8. 카드 페이즈에서 섯다 카드 처리, 베팅, 결과 정산이 진행된다.
9. 매치 종료 시 Dedi가 IOCP에 매치 종료 패킷을 보낸다.

현재 가장 큰 문제는 3번부터 7번까지의 준비 상태 공유가 시간 추측에 의존한다는 점이다.

## 3. 현재 가장 큰 서버/Dedi 문제

### 3.1 IOCP가 Dedi 준비 상태를 모른다

확인 위치:

- `X:\Project\Manager\Server\LobbyService.cpp:64`
- `X:\Project\Manager\Server\LobbyService.cpp:1389`
- `X:\Project\Manager\Server\Protocol_D.h:34`

현재 코드:

- `DEDI_GAME_START_DELAY_SECONDS = 15`
- Dedi 서버 실행 후 `std::this_thread::sleep_for(std::chrono::seconds(DEDI_GAME_START_DELAY_SECONDS))`
- 시간이 지나면 클라이언트에게 `S2C_GAME_START` 전송
- `D2L_SERVER_READY_NOTIFY` 같은 준비 완료 패킷은 현재 없다.

문제:

- Dedi가 실제로 listen 가능 상태인지 IOCP가 확인하지 않는다.
- 맵이 무거우면 15초는 부족하다.
- 150초, 300초로 늘려도 본질은 해결되지 않는다. 단지 문제 발생 시점을 늦출 뿐이다.
- 빠른 PC, 느린 PC, 에디터 실행, 패키징 실행, 원격 PC 환경마다 필요한 시간이 달라진다.

필요한 수정:

1. 서버 프로토콜에 `D2L_SERVER_READY_NOTIFY = 301` 추가.
2. 클라이언트 프로토콜 쪽에도 동일한 enum 값 추가.
3. Dedi 서버가 `RoomId`, `Port`, 가능하면 `ServerToken`을 포함해서 IOCP에 ready notify 전송.
4. IOCP는 고정 sleep 대신 roomId 기준 pending room을 보관한다.
5. ready notify를 받은 뒤에만 `S2C_GAME_START`를 클라이언트들에게 보낸다.
6. timeout은 "강제 GAME_START"가 아니라 오류 로그와 room rollback 또는 retry 용도로만 사용한다.

## 4. 카드 월드 드랍 문제

### 4.1 `NotEnoughDropZones`면 현재는 섬 카드 스폰 전체가 중단된다

확인 위치:

- `X:\Project\Manager\Source\Manager\Game\InGame\Card\CardGameService.cpp:1206`
- `X:\Project\Manager\Source\Manager\Game\InGame\Card\CardGameService.cpp:1209`

현재 코드 의미:

- 찾은 드랍존 수가 카드 그룹 수보다 적으면 `NotEnoughDropZones` 로그를 남긴다.
- 결과는 `AbortIslandCardSpawn`.

문제:

- 드랍존을 일부라도 찾았어도 전체 섬 카드 스폰이 중단된다.
- 여름 섬에서 드랍존 인식이 실패하면 카드가 아예 생성되지 않는다.
- 사용자가 말한 "Not Enough Drop Zones" 기억과 현재 코드가 맞다.

1. 드랍존이 부족하면 전체 중단이 아니라 fallback 모드로 전환.
2. 발견된 zone에는 정상 배치.
3. 부족한 zone은 season island bounds 또는 tagged actor bounds에서 보조 zone 생성.
4. 그것도 실패하면 서버 기준 ground trace fallback으로 안전 위치 산출.
5. 실패 로그는 유지하되, 가능한 카드는 최대한 스폰되게 한다.

## 5. 위치 동기화 문제

### 5.1 현재 위치 문제의 중심은 서버 권위 이전의 준비 상태 부족

현재 코드에서 위치 동기화는 단순히 "캐릭터 movement replication이 없음" 하나로 볼 문제가 아니다.

직접적인 구조 문제:

- 서버가 플레이어의 레벨 로딩 완료를 모른다.
- 서버가 TPS/Card stage 전환 완료를 모른다.
- 서버가 카드 스폰과 플레이어 이동을 페이즈 전환 직후 바로 진행한다.
- 클라이언트별 로딩 시간이 다르면 같은 서버 위치라도 클라에서 보이는 상태가 어긋날 수 있다.

필요한 수정:

1. 페이즈별 서버 권위 기준 anchor를 정한다.
2. 클라이언트 로딩 완료 ACK 이후 서버가 위치를 확정한다.
3. 서버가 `SetActorLocation` 또는 teleport를 수행한다.
4. 이후 클라이언트는 서버 위치를 따라가도록 한다.
5. 위치 보정은 로딩 완료 전이 아니라 로딩 완료 후에 실행한다.

## 13. 바로 다음 작업 제안

가장 먼저 해야 할 것은 `Dedi ready notify`다.

이유:

- 맵 로딩이 오래 걸리는 문제를 sleep으로 해결하려고 하면 계속 실패한다.
- Dedi가 실제 준비되기 전에 클라이언트를 보내면 이후 모든 문제가 연쇄로 생긴다.
- 이 작업이 끝나야 클라이언트 로딩 ACK와 카드 스폰 gate도 정확히 붙일 수 있다.

그 다음은 `클라이언트 로딩 완료 ACK`다.

이유:

- Dedi ready는 "서버가 접속 받을 준비"까지만 보장한다.
- 카드 스폰과 위치 보정은 "각 클라가 stage를 실제로 로딩 완료"한 뒤 해야 한다.

세 번째는 `카드 스폰 gate`다.

이유:

- 현재 코드에서 카드 스폰은 TPS 페이즈 시작 직후 실행된다.
- 이 위치를 gate 뒤로 옮겨야 여름 섬, 원격 PC, 느린 로딩 환경에서 안정화된다.

1. Dedi ready notify.

3. 카드 스폰 gate.
4. 카드 위치 fallback.

6. IOCP 안정성.

이 순서가 현재 코드 기준 가장 안전하다.

### 16.1 해결 2: `NotEnoughDropZones` 복구 처리

기존 문제:

- `SpawnRoundCardBundleForBattleRoyale()`에서 `IslandDropZones.Num() < IslandCardGroups.Num()`이면 바로 return했다.
- 이 상태에서는 한 섬이라도 드랍존이 부족하면 해당 라운드의 월드 카드 드랍이 통째로 생성되지 않았다.
- 특히 맵/섬 구성 차이, 드랍존 액터 인식 실패, Bounds 계산 실패가 있으면 `NotEnoughDropZones` 계열 로그 이후 카드가 안 보이는 현상으로 이어질 수 있었다.

반영 내용:

1. 드랍존 수가 카드 그룹 수보다 적어도 즉시 abort하지 않는다.
2. 드랍존이 1개 이상이면 부족한 그룹은 기존 드랍존을 modulo 방식으로 재사용한다.
3. 드랍존이 0개면 `CardBundleDropCenter`, `CardBundleDropExtent`, `CardIslandGroundTraceHalfHeight` 기반의 가상 fallback zone을 생성한다.
4. fallback zone의 `IslandKey`는 `BundleFallback`, `Source`는 `GeneratedBundleBounds`로 남긴다.
5. 같은 드랍존을 여러 카드 그룹이 공유할 수 있으므로 기존 위치 목록을 `TMap<int32, TArray<FVector>> ExistingLocationsByZoneIndex`로 zone index별 관리한다.

의미:

- 드랍존 인식이 완벽하지 않아도 카드 월드 드랍 전체가 0개가 되는 상황을 줄였다.
- 드랍존이 완전히 없을 때도 기존 번들 범위 설정을 이용해 최소한의 월드 드랍을 시도한다.
- 로그에서 `DropZoneRecover`, `GeneratedBundleBounds`, `ZoneIndex`를 보면 복구 경로를 탔는지 확인할 수 있다.

주의:

- 이 수정은 카드 드랍을 "안 하는 문제"를 막는 1차 복구다.
- 맵 자체 bounds가 잘못되어 있거나 fallback 중심/범위가 섬 밖이면 카드가 이상한 위치에 떨어질 수 있다.
- 따라서 멀티 테스트에서 카드가 보이긴 하지만 위치가 어긋나면 다음 단계는 `CardBundleDropCenter/Extent`, ground trace 결과, island zone actor 배치 값을 다시 봐야 한다.

### 16.2 해결 4: Dedi ticket 완전 검증

기존 문제:

- Dedi `PreLogin()`은 ticket이 비었는지, 숫자인지, 0보다 큰지만 확인했다.
- IOCP는 `S2C_GAME_START`의 ticket 값으로 session id를 그대로 보냈다.
- 따라서 "이 ticket이 실제로 이 방 시작 때 IOCP가 발급한 값인가", "이미 사용한 ticket인가"를 검증하지 못했다.

반영 내용:

1. `LobbyService::Room`에 `handoverTickets`를 추가했다.
   - 구조: `Session ID -> one-time Dedi ticket`
2. 방 시작 요청이 정상 조건을 통과하고 Dedi 실행 직전에 멤버별 랜덤 ticket을 생성한다.
3. `LaunchDedicatedServer()`에 `allowedTickets` 인자를 추가했다.
4. Dedi 실행 map option에 `?Tickets=티켓1,티켓2,...`를 붙인다.
   - 예: `...?RoomId=3?RequiredPlayers=2?Tickets=123456789,987654321`
5. `SendGameStartForRoom_Unsafe()`는 더 이상 session id를 ticket으로 보내지 않는다.
6. `SendGameStartForRoom_Unsafe()`는 해당 멤버의 `handoverTickets[mSid]`를 찾아 `S2C_GAME_START` ticket으로 보낸다.
7. Dedi `AMainGameMode::InitGame()`은 `Tickets` option을 파싱해서 `AllowedDediTickets`에 저장한다.
8. Dedi `AMainGameMode::PreLogin()`은 다음을 모두 검사한다.
   - ticket 없음: `MissingTicket`
   - ticket 형식 오류/0 이하: `InvalidTicket`
   - Dedi가 허용 ticket 목록을 못 받은 상태: `MissingTicketList`
   - 허용 목록에 없는 ticket: `UnknownTicket`
   - 이미 사용한 ticket 재사용: `ReusedTicket`
9. 정상 통과한 ticket은 `UsedDediTickets`에 추가하여 1회성으로 처리한다.
10. Dedi 실행 실패 rollback, 매치 종료, 방 이탈 경로에서 `handoverTickets`를 정리한다.

의미:

- 이제 Dedi는 단순히 숫자 ticket만 받는 것이 아니라, IOCP가 해당 방 시작 때 넘겨준 ticket 목록과 대조한다.
- 클라가 임의 숫자 ticket으로 Dedi에 직접 접속하는 흐름은 `UnknownTicket`으로 거부된다.
- 같은 ticket으로 두 번 들어오려는 흐름은 `ReusedTicket`으로 거부된다.

주의:

- 현재 ticket 목록은 Dedi 실행 command line/map option으로 전달된다. 로컬 개발/시험 기준으로는 충분하지만, 운영 보안까지 보려면 ticket 만료 시간, room id와 ticket의 서버 내부 저장소 대조, Dedi ready/match notify 인증까지 별도 설계가 필요하다.
- `InitGame` 로그에는 기존처럼 `Options` 전체가 찍히므로 `Tickets=` 값도 로그에 노출될 수 있다. 로그 정리 단계에서 ticket 원문 마스킹을 고려해야 한다.

### 16.3 해결 5: IOCP send/context/port pool 안정화

기존 문제:

- `SendPacket()`에서 최초 `WSASend`가 즉시 실패하면 실패한 패킷이 send queue에 남고 `sendInFlight` 상태만 내려갈 수 있었다.
- send completion 이후 다음 패킷 `WSASend`가 실패하는 경로에서 queue/ref 정리가 불명확했다.
- 여러 종료 경로가 `closesocket(client->sock)`을 직접 호출해 같은 socket close가 중복될 여지가 있었다.
- `ReleaseIO()`도 delete 직전에 다시 `closesocket(c->sock)`을 호출했다.
- `FreePort()`는 같은 Dedi port가 중복 반환되는지 검사하지 않았다.

반영 내용:

1. `CloseClientSocketOnce(ClientContext*)`를 추가했다.
   - `closeLock`으로 보호한다.
   - socket을 `INVALID_SOCKET`으로 먼저 바꾼 뒤 `shutdown/close`한다.
2. `MarkClientClosing(ClientContext*, reason)`을 추가했다.
   - `closing.exchange(true)` 최초 1회에만 `g_lobby.OnClientDisconnected()`를 호출한다.
   - 이후 socket close는 `CloseClientSocketOnce()`로 통일한다.
3. `ReleaseIO()`는 delete 직전에 직접 `closesocket`하지 않고 `CloseClientSocketOnce()`만 호출한다.
4. `SendPacket()` 시작 시 이미 closing인 context에는 더 이상 send를 쌓지 않는다.
5. 최초 `WSASend` 즉시 실패 시:
   - send queue clear
   - `sendInFlight=false`
   - `MarkClientClosing(..., "WSASendStartFailed")`
   - send ref `ReleaseIO`
   - send context delete
6. 부분 송신 재시도 실패 시:
   - send queue clear
   - `sendInFlight=false`
   - `MarkClientClosing(..., "WSASendPartialRetryFailed")`
   - send ref `ReleaseIO`
7. 다음 패킷 송신 실패 시:
   - send queue clear
   - `sendInFlight=false`
   - `MarkClientClosing(..., "WSASendNextFailed")`
   - send ref `ReleaseIO`
8. recv EOF, IOCP completion 실패, invalid packet size, recv repost 실패 경로도 `MarkClientClosing()`로 통일했다.
9. 최초 accept 직후 `WSARecv` 실패는 아직 로비 등록 전이므로 `OnClientDisconnected()`를 부르지 않고 `CloseClientSocketOnce()`와 `ReleaseIO()`만 수행한다.
10. `FreePort()`는 이미 free pool에 들어 있는 port면 다시 push하지 않고 `[DEDI] FreePort skipped duplicate ...` 로그만 남긴다.

의미:

- send 실패 후 실패 패킷/상태가 큐에 남아 다음 송신을 오염시키는 위험을 줄였다.
- 같은 client socket이 여러 완료 경로에서 중복 close되는 위험을 줄였다.
- Dedi port가 중복 반환되어 같은 port를 여러 방이 배정받는 위험을 줄였다.

주의:

- 이번 수정은 send 실패/close/중복 port 반환의 안정화다.
- 아직 "IN_GAME 방이 비었을 때 Dedi process를 어떻게 회수할 것인가", "Dedi가 비정상 종료됐을 때 IOCP가 port를 언제 회수할 것인가"는 별도 문제로 남아 있다.
- `ServerMain.cpp`의 C4819 인코딩 경고는 기존처럼 남아 있다.

### 17.1 이번 수정의 핵심 결론

기존 구조의 가장 큰 문제는 Dedi 서버가 TPS 월드를 완전히 로드한 클라이언트 상태와 무관하게 BattleRoyale phase 시작 직후 카드를 생성한다는 점이었다. 내 컴퓨터에서 서버/클라를 같이 켠 경우에는 로딩 타이밍이 비슷해서 우연히 보일 수 있지만, 다른 컴퓨터 클라이언트가 느리게 로드하면 서버는 이미 카드 위치를 계산하고 스폰했는데 클라는 아직 해당 스트리밍 레벨/월드 상태가 준비되지 않은 상태가 될 수 있다.

이번 수정 후 구조는 다음 순서가 된다.

1. Dedi가 TPS phase 진입을 시작한다.
2. `UTPSPhaseStrategy::OnPhaseStart()`는 더 이상 즉시 `SpawnRoundCardBundleForBattleRoyale()`를 호출하지 않는다.
3. 대신 `AMainGameMode::RequestBattleRoyaleCardSpawnAfterStreamReady()`를 호출해서 카드 스폰을 pending 상태로 둔다.
4. 각 클라이언트가 `ServerNotifyStreamLevelLoaded()`를 통해 `TPS_Game_Stage` 로딩 완료 ACK를 보낸다.
5. 서버는 `ClientLoadedStreamLevels`를 확인해서 필요한 클라이언트가 `TPS_Game_Stage` 로딩을 끝냈는지 검사한다.
6. 조건이 안 맞으면 `BattleRoyaleCardSpawnGateRetryInterval` 주기로 계속 재시도한다.
7. 조건이 맞으면 그때 서버가 카드 번들을 생성한다.
8. 카드 번들 생성이 끝난 직후에만 BattleRoyale 제한 시간 타이머를 시작한다.

이 방식의 의미:

- 로딩이 15초, 150초, 300초처럼 길어져도 고정 fallback 시간 때문에 먼저 카드가 생성되는 문제를 피한다.
- 맵이 늦게 뜨는 클라이언트 때문에 서버 카드 드랍이 너무 빨리 진행되는 문제를 줄인다.
- BattleRoyale 타이머가 로딩 중에 먼저 소모되어 카드가 스폰되기 전에 `TransitionToCard`로 넘어가는 문제를 막는다.

### 17.4 BattleRoyale 타이머 시작 위치 변경

이전에는 `StartBattleRoyalePhase()` 안에서 곧바로 `StartTimedServerPhase(EDediServerPhase::BattleRoyale, GetBattleRoyaleDuration())`를 호출했다.

이 구조의 문제:

- 맵 로딩이 BattleRoyale 제한 시간보다 길면, 카드가 생성되기 전에 BattleRoyale timeout이 먼저 올 수 있다.
- 그 경우 `StartTransitionToCardPhase()`가 호출되고 `ClearBattleRoyaleCardSpawnGate()`가 실행되어 pending 카드 스폰이 취소된다.
- 결과적으로 "로딩이 너무 긴 맵에서 카드가 안 보임" 문제가 다시 발생할 수 있다.

수정 후:

- `StartBattleRoyalePhase()`는 `BeginPhase(EGamePhase::TPS)` 이후 `CurrentServerPhase`를 `BattleRoyale`로 준비 상태만 만든다.
- `RemainingPhaseSeconds`는 0으로 두고 UI 시간도 0으로 맞춘다.
- `TrySpawnBattleRoyaleCardsWhenStreamReady()`가 실제 카드 스폰을 끝낸 뒤 `StartTimedServerPhase(EDediServerPhase::BattleRoyale, GetBattleRoyaleDuration())`를 호출한다.

의미:

- BattleRoyale 제한 시간은 "클라 로딩 ACK 완료 + 서버 카드 스폰 완료" 이후부터 돈다.
- 무거운 메인 게임 월드 때문에 로딩이 길어져도 카드 스폰 gate가 먼저 취소되지 않는다.

### 17.5 TPSPhaseStrategy 즉시 스폰 제거

`UTPSPhaseStrategy::OnPhaseStart()`에서 기존 즉시 스폰 호출을 제거했다.

이전:

### 18.4 회수 함수

추가 함수:


`CleanupDedicatedServerForRoom_Unsafe()` 역할:

- room의 `dedicatedPort`를 0으로 초기화.
- port를 free pool로 반환.
- `gameStartSent`를 false로 초기화.
- handover ticket 목록 제거.
- process handle이 있으면 상태 확인.

`SweepDedicatedServerProcesses()` 역할:

- 현재 room들이 들고 있는 Dedi process handle을 검사.
- Dedi process가 이미 종료되어 있으면:

  - port 반환.
  - handle close.
  - room을 `WAITING`으로 되돌림.
  - ready 상태를 host만 true로 재초기화.
  - room list/member list broadcast.
- process handle 조회 자체가 실패해도 무한 잔존하지 않도록 cleanup 처리.

스윕 호출 지점:

- `OnClientAccepted()`
- `OnClientDisconnected()`
- `OnPacket()`

### 19.2 재접속 티켓 정책

기존 문제:

- Dedi `PreLogin()`이 허용 ticket을 처음 사용한 순간 `UsedDediTickets`에 영구 등록했다.
- 클라이언트가 정상적으로 끊어진 뒤 IOCP가 같은 ticket을 다시 보내도 Dedi가 `ReusedTicket`으로 거부했다.
- 동시에 두 연결이 같은 ticket을 쓰는 것과 정상 재접속을 구분하지 못했다.

반영 정책:

- `UsedDediTickets`를 `ActiveDediTickets`로 교체했다.
- `PreLogin()`에서는 현재 접속 중인 ticket만 거부한다.
- `InitNewPlayer()` 성공 시 controller와 ticket을 연결한다.
- `Logout()`에서 해당 ticket을 active 집합에서 제거한다.
- 결과적으로 같은 ticket의 동시 접속은 거부하지만, 기존 접속의 `Logout` 처리가 끝난 뒤에는 재사용할 수 있다.
- ticket 원문과 전체 URL options를 Dedi 로그에 남기지 않는다.

현재 제한:

- 기존 Dedi 연결이 아직 timeout 처리되지 않은 순간 즉시 재접속하면 `TicketAlreadyActive`가 날 수 있다. 이전 연결의 `Logout` 후 재시도해야 한다.
- 클라이언트의 IOCP 소켓 자체가 끊겼을 때 자동으로 다시 connect/login하는 background retry는 이번 범위에 포함하지 않았다. 앱 재실행 또는 기존 로그인 흐름으로 IOCP에 다시 로그인하는 서버 재접속 경로를 완성한 것이다.

### 20.2 P0: Dedi 제어 패킷 인증

현재 코드:

- `D2L_SERVER_READY_NOTIFY`, `D2L_MATCH_END_NOTIFY`는 로그인하지 않은 임의 TCP 연결도 보낼 수 있다.
- Ready payload는 실제로 room id만 보내고 port는 보내지 않는다.
- IOCP는 ready port가 달라도 경고만 남기고 `SendGameStartForRoom_Unsafe()`를 실행한다.
- MatchEnd는 room id만 맞으면 현재 Dedi를 `TerminateProcess()`하고 방을 WAITING으로 되돌린다.

실제 위험:

- 외부 클라이언트가 room id를 추측해 Dedi 준비 전 게임 시작을 강제할 수 있다.
- 가짜 MatchEnd로 정상 매치를 종료할 수 있다.
- 같은 방의 이전 Dedi가 늦게 보낸 MatchEnd가 새 Dedi를 종료할 수 있다.

필요 작업:

1. 방 시작마다 `controlNonce` 또는 Dedi control token 생성.
2. `Room`에 token과 match generation 저장.
3. Dedi 실행 옵션에 `ControlToken`, `DediPort`, generation 전달.
4. Ready/MatchEnd payload에 room id, port, generation, token 포함.
5. IOCP에서 state/port/generation/token이 모두 일치할 때만 처리.
6. port mismatch는 경고 후 진행이 아니라 즉시 reject.
7. 가능하면 Dedi 전용 packet 연결은 loopback/local interface로 제한.

### 21.4 프로세스 종료와 포트 quarantine

기존에는 port를 pool에 먼저 반환한 뒤 `TerminateProcess()`했다.

현재 순서:

1. 필요하면 Dedi terminate.
2. `WaitForSingleObject()`로 최대 5초 실제 종료 대기.
3. UDP port를 `SO_EXCLUSIVEADDRUSE` probe bind로 검사.
4. 종료 확인과 port bind 가능 조건이 모두 맞으면 free pool 반환.
5. 종료 미확인 또는 port가 아직 사용 중이면 quarantine.
6. watchdog이 quarantine port를 다시 검사해 사용 가능할 때만 pool로 복귀.

따라서 종료 직후 같은 port가 아직 Dedi에 잡혀 있는데 다음 방에 재할당되는 경로를 막았다.

### 23.2 Dedi control ACK/retry

기존 문제:

- `NotifyIocpServerReady()`와 `NotifyIocpMatchEnd()`는 TCP 연결 후 packet을 한 번 `Send()`하고 끝났다.
- send가 성공해도 IOCP가 실제로 payload를 검증하고 room 상태에 반영했는지 Dedi는 알 수 없었다.
- Ready/MatchEnd는 control token 검증은 있었지만, 신뢰성 측면에서는 ACK/retry가 없었다.

반영:

1. 프로토콜에 ACK packet type 추가.
   - `L2D_MATCH_END_ACK = 302`
   - `L2D_SERVER_READY_ACK = 303`
2. `ServerMain::PacketTypeToString()`에 ACK 이름 추가.
3. `NetApi::SendDediControlAck()` 추가.
4. IOCP `LobbyService`는 Dedi control notify를 처리한 뒤 같은 TCP 연결로 ACK를 보낸다.
5. ACK payload는 다음 순서다.
   - `u32 roomId`
   - `u16 dediPort`
   - `u32 generation`
   - `u64 controlToken`
   - `u8 accepted`
6. Dedi `MainGameMode`는 control notify 송신 후 ACK header/payload를 끝까지 읽는다.
7. ACK type, room id, port, generation, token, accepted를 모두 검사한다.
8. 실패하면 `DediControlNotifyMaxAttempts`만큼 재시도하고, primary callback 주소가 전부 실패하면 기존 fallback `127.0.0.1:9000`도 같은 횟수로 재시도한다.

새 설정값:

```cpp
DediControlNotifyMaxAttempts = 3
DediControlAckTimeoutMs = 2000
DediControlRetryDelaySeconds = 0.5f
```

의미:

- 이제 Dedi Ready는 "IOCP에 bytes를 보냈다"가 아니라 "IOCP가 검증 후 accepted ACK를 돌려줬다"까지 확인한다.
- Ready notify가 실패하면 Dedi가 즉시 포기하지 않고 같은 endpoint를 재시도한다.
- MatchEnd도 IOCP의 ACK를 기다린다.
- 정상 MatchEnd 처리 시 IOCP가 Dedi process를 즉시 `TerminateProcess()`하지 않고, room 상태와 port quarantine만 정리한다. Dedi는 기존 10초 self shutdown timer로 내려간다. 이렇게 해야 MatchEnd ACK가 Dedi에 도달할 시간이 생긴다.

주의:

- malformed payload처럼 room/port/generation/token을 파싱할 수 없는 경우에는 ACK를 보낼 수 없다.
- MatchEnd ACK가 유실된 뒤 Dedi가 재시도하면 IOCP room은 이미 WAITING으로 정리됐을 수 있다. 이 경우 두 번째 notify는 rejected ACK가 될 수 있다. 다만 첫 번째 notify가 IOCP에 반영된 상태라면 room 정리는 이미 완료된 것이다.

### 23.3 Loading Gate 미응답 client 정책

기존 문제:

- disconnect한 player는 `Logout()`에서 ACK map에서 제거되어 Gate가 재평가됐다.
- 하지만 연결은 살아 있는데 클라이언트가 stream level ACK를 영원히 보내지 않는 경우, 카드 스폰 Gate 또는 TPS/Card 전환 Gate가 무기한 대기할 수 있었다.
- 기존 300초 빠른 retry 이후 5초 watchdog으로 계속 기다리는 구조는 "무거운 맵을 기다리는 것"에는 안전하지만, "살아 있는데 ACK가 절대 오지 않는 client"를 분리하지 못했다.

반영:

1. 서버가 level 전환 요청을 보낼 때 player별 requested level과 request time을 저장한다.
   - `ClientRequestedStreamLevels`
   - `ClientStreamRequestTimes`
2. `BroadcastSwitchLevel()`은 `SwitchToLevel()` 직후 `RegisterClientStreamLevelRequest()`를 호출한다.
3. 재접속/중간 입장 phase sync도 `Client_SwitchToLevel()` 직후 request를 등록한다.
4. 정상 stream ACK가 오면 loaded map에 저장하고 request/excluded 상태를 제거한다.
5. `Logout()`은 loaded/request/excluded 상태를 모두 제거한다.
6. `HaveRequiredClientsLoadedStreamLevel()`은 excluded player를 target count에서 제외한다.
7. `TrySpawnBattleRoyaleCardsWhenStreamReady()`와 `WaitForTransitionStreamLevelIfNeeded()`는 Gate 판단 전에 `ExcludeTimedOutStreamGateClients()`를 호출한다.

새 설정값:

```cpp
StreamGateClientAckTimeoutSeconds = 600.0f
bKickStreamGateTimedOutClients = true
```

동작:

- 기본 600초 동안은 기존처럼 ACK를 기다린다.
- 600초를 넘겼는데 해당 player가 target level ACK를 보내지 않으면 서버가 `StreamGate timeout` error 로그를 남긴다.
- 해당 player는 Gate 대상에서 제외된다.
- `bKickStreamGateTimedOutClients`가 true이면 해당 client에 `ClientReturnToMainMenuWithTextReason("StreamLevelLoadTimeout")`를 보낸다.
- 제외 후 남은 player 기준으로 required count를 다시 계산하므로, 한 명의 무응답 client 때문에 전체 매치가 영구 정지되는 문제를 줄인다.

의미:

- 맵 로딩이 오래 걸리는 정상 상황은 여전히 기다린다.
- ACK 없는 강제 카드 스폰은 하지 않는다.
- "무한 로딩/응답 없음" client만 분리해서 남은 client 기준으로 Gate를 진행한다.

betting 중 disconnect 후 처리:

1. 남은 active player가 1명 이하이거나 bet이 settled 상태면 `ResolveSeotdaRoundResult("DisconnectAutoFold")` 실행
2. 이 경우 GameMode phase가 아직 `CardGame`이면 `FinishCurrentServerPhase("SeotdaDisconnectSettled")` 호출
3. 아직 플레이어가 남아 있고 정산 조건이 아니면 `AdvanceSeotdaBettingTurn()` 호출

`HandlePlayerDisconnectedAfterLogout()` 동작:

- `Logout()`의 `Super::Logout()` 이후 호출된다.
- 선택 단계에서 끊긴 플레이어가 실제 PlayerController iterator에서 빠진 뒤 `TryResolveSeotdaRoundIfReady()`를 다시 호출한다.
- 이로써 선택 완료 대상 수가 disconnected player 때문에 계속 막히는 일을 줄인다.

`ReattachPlayerAfterReconnect()` 보강:

- betting이 이미 시작되었는데 해당 ticket에 turn order slot이 없으면, 저장된 seotda state를 다시 active state로 붙이지 않는다.
- 이유: 선택 단계에서 끊긴 유저를 제외하고 betting이 시작된 뒤, 그 유저가 다시 붙으면 turn order에는 없는데 active state에만 들어가 정산이 영원히 false가 될 수 있기 때문이다.
- 이 케이스는 `Reconnect SeotdaStateDrop Reason=BettingStartedWithoutTurnSlot` 로그로 남긴다.

라운드 종료/리셋 시:

- `ResetSeotdaRoundStates()` 시작 시 `ReconnectSeotdaStates`, `ReconnectTurnOrderIndices`를 비운다.
- `ResolveSeotdaRoundResult()` 성공/실패 후에도 reconnect seotda state를 비운다.
- 오래된 이전 라운드 seotda state가 뒤늦은 재접속으로 다시 붙는 문제를 막는다.

### 24.6 이번 수정으로 해결된 것

## 26. 2026-07-11 영속 월드 로딩 Gate 수정과 Summer NavMesh 원인 확정

### 26.1 실제 레벨 구조 재확인

`Content/InGame/System/Main_Game_World.umap`의 package/export 구조를 직접 확인한 결과는 다음과 같다.

- `Main_Game_World`의 PersistentLevel에 `BPP_MAP_Summer`, `Spring`, `Autumn`, `Winter` 4개 섬이 직접 들어 있다.
- 같은 PersistentLevel에 `NavMeshBoundsVolume_0`과 `RecastNavMesh-Default`가 직접 들어 있다.
- 동적 스트리밍 레벨로 등록된 것은 `Card_Game_Stage` 하나뿐이다.
- `TPS_Game_Stage.umap`은 `Floor_0`만 가진 별도 맵이며 `Main_Game_World`의 스트리밍 child가 아니다.

따라서 기존 코드가 배틀로얄 준비 대상으로 사용한 `TPS_Game_Stage`는 현재 맵 구조에서는 찾을 수 없는 이름이다. 서버와 클라이언트가 `LoadStreamLevel("TPS_Game_Stage")`를 호출해도 `ULevelStreaming` object가 생기지 않는 것이 정상이다.

### 26.2 기존 로딩 Gate의 실제 오류

최신 실행 로그에서 기존 Gate는 다음 상태였다.

- `ServerLevelFound=0`
- `ServerLoaded=0`
- `ServerVisible=0`
- `NavBuilding=1`
- 클라이언트 ACK는 `2/2`

그런데 기존 `OnClientStreamLevelLoaded()`는 `Found/Loaded/Visible`이 모두 false여도 경고만 출력하고 `Server_ReportStreamLevelLoaded()`를 호출했다. 서버도 클라이언트 ACK만 충족되면 `CardGateProceedWithServerNotReady`를 남기고 카드 생성을 진행했다.

추가로 서버 `BroadcastSwitchLevel()`은 새 레벨 load만 수행하고 이전 `Card_Game_Stage`를 서버에서 unload하지 않았다. 클라이언트만 카드 스테이지를 내리고 서버는 계속 보유할 수 있는 비대칭 구조였다.

### 26.3 영속 월드/스트리밍 레벨 구분 구현

배틀로얄 준비 target을 `Main_Game_World`로 변경했다. 이 이름은 스트리밍 load 명령이 아니라 현재 PersistentLevel 준비 상태를 나타내는 target으로 사용한다.

서버 동작:

- `BattleRoyale`, `TransitionToBattle`의 target은 `Main_Game_World`이다.
- `Main_Game_World`에는 `LoadStreamLevel`/`UnloadStreamLevel`을 호출하지 않는다.
- 현재 map name이 `Main_Game_World`인지, PersistentLevel이 존재하는지, world가 BeginPlay를 마쳤는지 확인한다.
- 카드 페이즈 진입 시 PersistentLevel은 그대로 두고 `Card_Game_Stage`만 load한다.
- 배틀로얄 복귀 시 서버와 클라이언트 모두 `Card_Game_Stage`를 unload한다.
- 서버도 pending unload의 실제 `Loaded/Visible=false`를 Gate 조건으로 확인한다.

클라이언트 동작:

- `Main_Game_World` target은 현재 map name과 `HasBegunPlay()`로 확인한다.
- 스트리밍 target은 `ULevelStreaming` 존재, `IsLevelLoaded()`, `IsLevelVisible()`을 모두 확인한다.
- 이전 스트리밍 레벨이 실제로 unloaded되기 전에는 다음 target ACK를 보내지 않는다.
- 미준비 상태에서는 0.25초 간격으로 다시 확인한다.
- 첫 대기와 40회마다만 상태 로그를 출력해 polling 로그 비용을 제한한다.
- 준비 완료 후 한 요청당 ACK는 한 번만 보낸다.
- latent action UUID를 고정값 1/2에서 요청마다 증가하는 값으로 변경해 여러 라운드/재접속 시 기존 latent action과 충돌하지 않게 했다.
- latent callback이 누락돼도 readiness polling이 ACK를 복구한다.

### 26.4 카드 생성 Gate의 새 강제 조건

이제 배틀로얄 카드는 아래 조건이 동시에 참일 때만 생성한다.

1. 서버 현재 map이 `Main_Game_World`
2. 서버 PersistentLevel 존재 및 BeginPlay 완료
3. 서버 pending stream unload 완료
4. 서버 NavigationSystem 존재
5. 서버 Navigation build/lock 종료
6. 필요한 클라이언트의 실제 level-ready ACK 완료

하나라도 false면 카드를 생성하지 않고 계속 대기한다. 기존 `CardGateProceedWithServerNotReady` fallback 진행 경로는 제거했다. `BattleRoyaleCardSpawnGateMaxRetries`에 도달해도 생성 fallback을 하지 않고 긴 간격으로 계속 대기한다.

### 27.2 정확한 원인

`ScheduleBattleRoyaleCardSpawnGateRetry()`는 0.5초짜리 non-looping one-shot timer를 설정한다. 이 타이머가 만료되면 `RetryBattleRoyaleCardSpawnGate()`가 실행되고, 준비가 끝나지 않았으면 같은 함수 흐름에서 다음 one-shot timer를 예약하려고 한다.

문제는 Unreal Engine 5.7의 실행 중 타이머 상태 규칙이다.

- timer delegate 실행 중 기존 timer 상태는 `ETimerStatus::Executing`이다.
- `FTimerManager::IsTimerActive()`는 timer가 존재하고 `Paused`가 아니면 `true`를 반환한다.
- 따라서 실행 중 one-shot timer도 `IsTimerActive()==true`이다.
- 재시도 callback 안에서 `ScheduleBattleRoyaleCardSpawnGateRetry()`를 호출하면 기존 handle이 아직 active라고 판단해 즉시 return한다.
- callback이 끝나면 non-looping timer는 TimerManager에서 제거된다.
- 결과적으로 기존 timer도 사라지고 다음 timer도 생성되지 않아 Gate polling이 `Retry=1`에서 영구 중단됐다.

이 동작은 UE 5.7 설치 엔진의 `TimerManager.h`와 `TimerManager.cpp` 구현 및 실제 서버 로그의 `Retry=1` 정지로 교차 확인했다.

### 27.3 수정 내용

수정 파일:

- `Source/Manager/Game/InGame/MainGameMode.cpp`

수정 함수:

- `AMainGameMode::RetryBattleRoyaleCardSpawnGate()`

수정 방식:

```cpp
void AMainGameMode::RetryBattleRoyaleCardSpawnGate()
{
    if (UWorld* World = GetWorld())
    {
        // Executing one-shot timers still report active, so release the handle before rescheduling.
        World->GetTimerManager().ClearTimer(BattleRoyaleCardSpawnGateTimerHandle);
    }

    TrySpawnBattleRoyaleCardsWhenStreamReady();
}
```

`ClearTimer()`는 실행 중인 기존 one-shot timer를 제거하면서 외부 handle도 invalidate한다. 그 뒤 Gate 상태를 검사하면 준비되지 않은 경우 `ScheduleBattleRoyaleCardSpawnGateRetry()`가 같은 handle에 새 timer를 정상적으로 설정할 수 있다.

### 28.2 `NavBuilding`을 하드 Gate로 사용할 수 없는 이유

기존 `BuildServerLevelGateState()`는 `UNavigationSystemV1::IsNavigationBeingBuiltOrLocked(World)`를 사용했다. 이 값은 단순히 "현재 NavMesh 타일을 빌드 중"만 뜻하지 않는다. navigation lock, build 진행, dirty area 대기 상태를 하나의 boolean으로 합친 진단값이다.

현재 프로젝트는 runtime navigation generation을 사용한다. 큰 `Main_Game_World`에서는 플레이 가능한 상태가 됐어도 dirty/lock 상태 때문에 이 값이 장시간 또는 계속 `true`일 수 있다. 그러므로 이를 전체 카드 생성의 필수 조건으로 두면 다음 문제가 생긴다.

- 카드별 배치 함수는 Summer에서 ground trace fallback으로 정상 위치를 찾을 수 있어도 호출 자체가 되지 않는다.
- Autumn, Spring, Winter처럼 이미 정상 배치됐던 섬도 Summer/Nav 전역 상태 하나 때문에 함께 막힌다.
- 시간값을 120초, 150초, 300초로 늘려도 boolean이 해제되지 않으면 결과는 동일하다.

수정 후 `NavSystem`, `NavBuilding`은 `CardGateStatus`에 계속 출력하되 `NavDiagnosticOnly=1`로 표시한다. 서버 월드 Gate의 실제 필수 조건은 다음뿐이다.

- World가 BeginPlay를 완료함
- 목표 level을 찾음
- 목표 level이 loaded 상태임
- 목표 level이 visible 상태임
- 이전 streaming level unload가 완료됨

Navigation 사용 가능 여부는 각 카드 위치를 계획하는 `PickIslandCardDropLocation()` 내부에서 판단한다. Navigation 위치를 못 찾으면 기존 검증된 ground trace fallback을 시도하며, 두 방식 모두 실패한 카드가 하나라도 있으면 번들 전체를 거부한다.

### 28.3 서버 카드 생성의 plan/commit 원자화

수정 파일:

- `Source/Manager/Game/InGame/Card/CardGameService.h`
- `Source/Manager/Game/InGame/Card/CardGameService.cpp`

기존 함수는 반환값이 없었고 카드별 위치 또는 actor 생성이 실패하면 해당 카드만 `continue`했다. 따라서 20장 중 일부만 생성돼도 GameMode는 생성 완료로 표시하고 배틀로얄 타이머를 시작할 수 있었다.

새 시그니처:

```cpp
bool SpawnRoundCardBundleForBattleRoyale(TArray<int32>& OutSpawnedCardInstanceIds);
```

새 처리 순서:

1. 섬 그룹 수 이상의 서로 다른 drop zone이 있는지 검사한다.
2. actor를 한 개도 만들지 않은 상태에서 모든 카드의 위치를 먼저 계획한다.
3. 위치 한 곳이라도 실패하면 `CardBundlePlanRejected`를 남기고 actor를 전혀 만들지 않는다.
4. 모든 위치가 확보된 경우에만 actor 20개 생성을 commit한다.
5. actor 생성 한 개라도 실패하거나 instance ID 수/active actor 수가 계획 수와 다르면 방금 만든 actor를 전부 제거한다.
6. 실패 transaction에서 생성한 server card record도 제거한다.
7. 정확히 전체 수가 생성된 경우에만 `true`와 전체 instance ID 목록을 반환한다.

즉, 새 코드에는 "일부 카드만 드롭된 상태"가 성공 상태로 존재하지 않는다.

### 28.4 클라이언트 카드 번들 가시성 ACK

수정 파일:

- `Source/Manager/Game/InGame/MainPlayerController.h`
- `Source/Manager/Game/InGame/MainPlayerController.cpp`

서버가 전체 카드를 만들었다는 사실만으로 원격 클라이언트 replication 완료를 보장할 수 없다. 이를 위해 bundle generation과 기대 instance ID 전체 목록을 reliable Client RPC로 보낸다.

```text
Client_ExpectCardBundle(Round, BundleGeneration, ExpectedInstanceIds)
```

클라이언트는 0.25초 간격으로 `ACardDropActor`를 검사한다. 기대 ID 각각에 대해 다음 조건이 모두 맞아야 한다.

- actor가 존재함
- `CardInstanceId > 0`
- `CardID != None`
- picked up 상태가 아님
- hidden 상태가 아님

하나라도 없으면 다음 로그를 주기적으로 남기고 ACK하지 않는다.

```text
[CL] CardBundleReadyWait Round=... Generation=... Visible=17/20 Missing=[...]
```

전체가 확인된 경우에만 서버로 다음 reliable RPC를 보낸다.

```text
[CL] CardBundleReadyAck Round=... Generation=... Visible=20/20
Server_ReportCardBundleReady(...)
```

기존 client level ACK timer에도 실행 중 one-shot handle을 먼저 clear하는 수정을 적용했다. 따라서 느린 원격 클라이언트에서 level readiness 재시도 역시 한 번 뒤 멈추지 않는다.

- 각 플레이어는 보유 카드 3장 중 모두에게 공개할 카드 1장을 선택한다.
- 선택하지 않은 나머지 2장이 해당 플레이어의 섯다 패가 된다.
- 공개 카드는 `AMainPlayerState::RevealedCard`로 일반 복제하며 모든 클라이언트가 확인할 수 있다.
- 전체 보유 카드 배열 `OwnedCards`는 기존과 같이 `COND_OwnerOnly`로 유지하므로 숨은 2장은 상대에게 복제되지 않는다.
- 서버는 카드 3장의 소유권 레코드를 모두 검증한 뒤 공개 카드와 숨은 패를 분리한다.
- 모든 접속 플레이어가 공개 카드 선택을 제출한 뒤에만 기존 섯다 베팅 로직이 시작된다.
- 공개 카드와 선택 완료 상태는 재접속 스냅샷에 포함한다.

### 31.2 배틀 로얄 카드 버리기

- 상점에서 버린 카드는 기존처럼 제거 상태가 된다.
- 배틀 로얄에서 버린 카드는 새 인스턴스를 만들지 않고 동일한 `CardInstanceId`와 `CardID`로 플레이어 현재 위치의 지면에 다시 생성한다.
- 수동 버리기 위치는 NavMesh에 의존하지 않고 플레이어 위치 기준 지면 trace를 사용한다.
- 월드 액터 생성에 실패하면 보유 카드 목록과 서버 카드 레코드를 변경하지 않는다.
- 생성 성공 후에만 소유권을 해제하고 레코드를 `WorldDrop`으로 전환하므로 다른 플레이어가 기존 픽업 RPC로 주울 수 있다.

### 31.3 사망 시 골드 드롭

- `UAbility_Death`의 전 카드 드롭 호출을 제거했다.
- `UCardGameService::DropOwnedCardsFromPlayer` 함수도 제거해 사망 시 카드 드롭 경로를 코드에서 폐기했다.
- 배틀 로얄 사망 시 `AMainGameMode::DropGoldFromPlayer`가 서버 권위로 골드 드롭을 생성한다.
- 기본 드롭량은 `DeathGoldDropAmount=1000`이며 GameMode 기본값/블루프린트에서 변경할 수 있다.
- 보유 골드가 1000보다 적으면 현재 보유량까지만 드롭하고 골드는 음수가 되지 않는다.
- 골드 액터 생성 성공 뒤에만 사망자의 `HoldingGold`를 차감한다.
- 살아 있는 플레이어가 `AGoldDropActor`와 겹치면 해당 금액을 획득하고 액터가 제거된다.
- 남은 골드 드롭은 배틀 종료, 게임 종료, 경기 중단 때 정리한다. 회수되지 않은 골드는 사망 손실로 남는다.

### 31.4 최종 승리 조건과 순위

- 최종 순위 기준은 누적 획득량의 별도 카운터가 아니라 경기 종료 시점의 현재 `HoldingGold`다.
- 따라서 베팅, 상점 구매, 사망 골드 드롭, 골드 픽업 결과가 모두 순위에 반영된다.
- 골드 내림차순으로 정렬하며 동일 골드는 공동 순위를 사용한다. 예: `#1`, `#1`, `#3`.
- 동점이 아니면 1위 플레이어 이름을 IOCP 승자 이름으로 전송한다.
- 공동 1위이면 공동 승자 이름과 골드를 동점 문자열로 전송한다.
- 최종 클라이언트 결과에는 정렬된 전체 순위를 표시한다.
- 재접속 유예 중인 연결 해제 플레이어도 저장된 이름과 골드로 최종 순위에 포함한다.

7. 최종 결과가 현재 골드 내림차순이며 사망 손실과 골드 픽업이 순위에 반영되는지 확인한다.

## 32. 2026-07-16 섯다 서버 권위 안정화 및 최종 빌드

### 32.1 공개 카드 선택 ACK

- 클라이언트는 공개 카드 선택 RPC를 보낸 직후 성공으로 확정하지 않는다.
- 서버의 `UCardGameService::SubmitSeotdaSelection`이 페이즈, 카드 수, 선택 수, 카드 소유권과 서버 레코드를 검증한다.
- 서버는 `Client_ReceiveSeotdaSelectionResult`로 승인 여부와 실패 사유를 요청 클라이언트에 돌려준다.
- UI는 ACK 대기 중 선택/제출을 잠그며, 거절되면 잠금을 풀고 다시 선택할 수 있게 한다.
- rate limit과 CardGameService 부재도 각각 `RateLimited`, `ServerUnavailable` 거절 ACK를 보낸다.

### 32.2 선택 및 베팅 타임아웃

- 공개 카드 선택 기본 제한시간은 `60초`다.
- 제한시간이 끝난 미제출 플레이어는 서버가 첫 번째 카드를 공개 카드로 자동 선택한다.
- 자동 선택까지 실패하면 라운드를 강제로 정리하고 다음 페이즈로 진행하여 무한 대기를 막는다.
- 선택 전용 타이머를 시작할 때 기존 CardGame 일반 페이즈 타이머를 해제한다. 무거운 클라이언트가 늦게 로드되는 동안 일반 타이머가 먼저 페이즈를 넘기는 경쟁 조건을 제거했다.
- 베팅 턴 기본 제한시간은 `30초`다.
- 콜 금액이 없으면 `Check`, 콜이 필요하면 `Die`를 서버가 자동 수행한다.
- 유효한 다음 플레이어가 없거나 턴 목록이 비면 라운드를 정리하고 페이즈를 종료한다.

### 32.3 올인과 동점 처리

- 플레이어 골드가 0이 되면 서버 라운드 상태에 `bAllIn`을 기록한다.
- 올인 플레이어는 이후 턴 대상과 타임아웃 대상에서 제외한다.
- 다른 플레이어의 레이즈가 발생해도 올인 플레이어의 행동 완료 상태는 다시 풀리지 않는다.
- 베팅 완료 판정은 올인 플레이어가 현재 최고 베팅액보다 적게 냈더라도 정산 가능한 상태로 본다.
- 동일한 최상위 패가 여러 명이면 팟을 균등 분배한다.
- 나머지 골드는 플레이어 이름과 PlayerId로 정한 안정적인 순서에 따라 1골드씩 배분한다.
- 현재 규칙은 단일 팟 방식이다. 서로 다른 금액으로 여러 명이 올인할 때 포커식 사이드팟을 분리하는 기능은 구현하지 않았다.

### 32.4 최종 골드 순위의 연결 해제 보존

- 경기 시작 후 참가자의 Dedi ticket, 이름, 최신 골드를 `MatchParticipantGoldLedger`에 보존한다.
- 접속, 재접속, 연결 해제 스냅샷 저장, 재접속 유예 만료 때 원장을 갱신한다.

## 34. 2026-07-21 섯다 공개 카드와 최종 패 제출 분리

이 항목은 31장과 32장에 기록된 "공개 카드 선택이 곧 제출 완료"라는 이전 구현 설명을 대체한다.

### 34.1 확인된 원인

- 기존 `UCardGameService::SubmitSeotdaSelection()`은 선택 수를 1장으로 검사했다.
- 선택한 1장을 공개 카드로 저장한 직후 나머지 2장을 자동으로 최종 패로 계산했다.
- 같은 요청에서 `bSubmitted=true`까지 기록했으므로 공개 ACK 뒤에는 별도의 최종 제출이 `AlreadySubmitted`로 거부됐다.
- 따라서 UI의 Reveal과 Submit이 충돌한 것이 아니라 서버가 두 행동을 하나의 상태 전이로 구현한 것이 직접 원인이었다.

### 34.2 수정된 서버 상태와 순서

1. `RevealSeotdaCard`: 보유 카드 3장 중 정확히 1장을 검증하고 `bRevealConfirmed`와 `RevealedCardInstanceId`만 저장한다.
2. `SubmitSeotdaSelection`: 공개 확정이 끝난 플레이어에게서 정확히 2장을 다시 받아 패를 계산하고 `bSubmitted`를 기록한다.
3. 모든 참가자가 최종 2장 제출을 마쳐야 `StartSeotdaBettingRound()`가 실행된다.

공개 카드는 정보 공개용이다. 기존 3장 중 2장 선택 규칙을 보존하므로 공개한 카드가 최종 패에 포함될 수도 있고 제외될 수도 있다. 카드 레코드의 `Used` 전환과 패 계산은 공개 시점이 아니라 최종 제출 성공 시점에만 수행한다.

### 34.3 RPC와 UI 분리

- 공개 요청/ACK: `Server_RevealSeotdaCard`, `Client_ReceiveSeotdaRevealResult`
- 최종 제출/ACK: `Server_SubmitSeotdaSelection`, `Client_ReceiveSeotdaSelectionResult`
- 공개와 제출은 서로 다른 rate-limit 상태와 결과 serial을 사용한다.
- UI는 공개 단계에서 1장만 선택할 수 있다.
- 공개 승인 후 기존 선택 표시를 비우고 최종 패 단계에서 2장까지 선택할 수 있다.
- 공개 요청 대기와 최종 제출 대기를 별도 상태로 관리하므로 한 응답이 다른 단계의 잠금을 해제하거나 제출 완료를 덮어쓰지 않는다.
- 키보드 입력 경로도 동일하게 1장 공개, 2장 최종 제출 순서를 사용한다.

### 34.4 타임아웃, 재접속, 비공개 정보

3. 각 클라이언트가 3장 중 2장을 새로 선택하고 `Submit Final Hand`를 누른다.
4. 한 명만 최종 제출한 동안에는 베팅이 시작되지 않는다.
5. 전원이 최종 제출하면 베팅 턴이 시작된다.
6. 아무 행동도 하지 않은 플레이어는 60초 뒤 자동 공개와 자동 제출이 순서대로 처리된다.

# Manager 섯다 공개 카드/최종 패 분리

- 작성일: 2026-07-21
- 대상: Dedicated Server 권위 섯다 선택 흐름, Controller RPC, 임시 섯다 UI, 카드 입력
- 상태: 수정 번들 및 정적 검증 완료, 실제 프로젝트 적용 후 Client/Dedi 빌드 필요

## 1. 사용자 요구 흐름

1. 보유 카드 3장 중 모두에게 공개할 카드 1장을 선택한다.
2. 공개 선택과 별도로 최종 섯다 패 2장을 다시 선택하고 제출한다.
3. 모든 플레이어의 최종 제출이 끝난 뒤 베팅을 시작한다.

공개 카드와 최종 패 선택은 서로 다른 행동이다. 공개 카드는 최종 패에 포함될 수도 있고 빠질 수도 있다.

## 2. 기존 코드의 실제 문제

기존 `SubmitSeotdaSelection()`은 다음 작업을 한 번에 수행했다.

1. 선택 수가 정확히 1장인지 검사
2. 선택한 카드를 `RevealedCard`로 복제
3. 선택하지 않은 나머지 2장으로 즉시 패 계산
4. `bSubmitted=true` 기록
5. 전원 완료 시 베팅 시작

따라서 공개 요청이 성공한 순간 서버 관점에서는 최종 제출도 끝났다. 사용자가 그 뒤 2장을 제출하려 하면 `AlreadySubmitted`가 되는 것이 정상적인 기존 동작이었다. UI 버튼 간 충돌이 아니라 서버 상태 모델이 한 단계뿐인 것이 원인이었다.

## 3. 서버 수정

### 3.1 공개 확정

`RevealSeotdaCard()`를 새로 분리했다.

- CardGame 페이즈와 서버 Authority 확인
- 플레이어와 PlayerState 확인
- 카드 3장 보유 확인
- 정확히 1장 선택 확인
- 세 카드 모두 서버 카드 레코드의 소유권/상태/CardID 일치 확인
- `bRevealConfirmed`와 `RevealedCardInstanceId`만 저장
- `AMainPlayerState::SetRevealedCard()`로 공개 카드만 전체 복제
- 패 계산, `Used` 전환, 베팅 시작 검사는 수행하지 않음

### 3.2 최종 패 제출

기존 `SubmitSeotdaSelection()`은 최종 2장 제출 전용으로 바꿨다.

- 정확히 2장 선택 확인
- 공개 확정 선행 여부 확인
- 서버 상태의 공개 카드와 PlayerState 공개 카드 일치 확인
- 선택한 두 장의 소유권과 서버 레코드 재검증
- `FSeotdaRuleService::EvaluateSeotdaHand()`로 최종 패 계산
- `SelectedCardInstanceIds`, `HandResult`, `bSubmitted` 기록
- 최종 제출 성공 시 보유한 라운드 카드 3장을 `Used`로 전환
- 모든 참가자가 `bSubmitted`일 때만 베팅 시작

## 4. Controller와 UI 수정

- 공개 RPC와 ACK를 최종 제출 RPC/ACK와 분리했다.
- 공개와 제출 rate limit을 분리해 정상적인 연속 단계가 서로 제한하지 않게 했다.
- Controller UI 상태에 공개 확정 여부와 공개 결과 serial/사유를 추가했다.
- 공개 실패가 이미 확정된 최종 제출 상태를 거짓으로 되돌리지 않게 했다.
- 위젯의 공개 단계는 선택 최대 1장, 제출 단계는 선택 최대 2장이다.
- 공개 승인 시 선택 플래그와 선택 애니메이션을 모두 초기화한다.
- 세 번째 최종 패 카드는 상태와 애니메이션 모두 선택되지 않는다.
- 버튼 문구는 `Reveal Public Card`, `Submit Final Hand`, `Submitted / Waiting` 순서로 바뀐다.
- 베팅 요청은 최종 패 제출 전에는 클라이언트와 서버 양쪽에서 거부된다.

## 5. 타임아웃과 재접속

- 기존 60초 선택 타이머는 현재 공개와 최종 제출을 합친 하나의 기한이다.
- 타임아웃 콜백은 먼저 모든 미공개 플레이어를 자동 공개 처리한다.
- 이어서 모든 미제출 플레이어에게 첫 두 장을 최종 패로 자동 제출한다.
- 일부 자동 처리가 실패하면 기존 강제 정리/페이즈 진행 fallback을 유지한다.
- `FSeotdaPlayerRoundState` 전체가 재접속 상태로 복사되므로 `bRevealConfirmed`도 함께 보존된다.

## 6. 개인정보 복제 확인

- `OwnedCards`: `COND_OwnerOnly`, 본인 클라이언트에만 복제
- `RevealedCard`: 조건 없는 복제, 모든 클라이언트에 공개
- `PublicCardCount`: 전체 복제, 상대의 카드 수만 표시 가능

최신 코드가 이미 위 조건으로 구현되어 있어 PlayerState는 수정하지 않았다.

## 7. 빌드 후 검증표

1. 공개 전에는 한 장만 선택 가능해야 한다.
2. 공개 버튼을 누른 뒤 서버 ACK 전에는 카드와 버튼이 잠겨야 한다.
3. 공개 승인 후 선택이 0장으로 초기화되고 공개 카드가 모든 클라이언트에 보여야 한다.
4. 최종 패 단계에서 서로 다른 두 장을 동시에 선택할 수 있어야 한다.
5. 세 번째 카드를 누르면 선택 수와 애니메이션이 2장을 넘지 않아야 한다.
6. 공개한 카드를 포함한 2장 제출과 제외한 2장 제출이 모두 허용돼야 한다.
7. 한 플레이어만 최종 제출했을 때 베팅이 시작되면 안 된다.
8. 전원 최종 제출 후에만 베팅 턴이 시작돼야 한다.
9. 60초 방치 시 `AutoReveal` 다음 `AutoSubmit` 로그가 순서대로 나와야 한다.
10. 공개 후 연결을 끊었다가 재접속하면 공개 단계는 유지되고 최종 제출만 다시 할 수 있어야 한다.

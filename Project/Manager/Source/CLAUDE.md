# CLAUDE.md

## 이 문서의 목적
Claude가 이 프로젝트에서 코드를 작성/수정할 때 지켜야 할 규칙. 특히:
1. 지시를 임의로 축소 해석하지 말고, 애매하면 먼저 확인할 것
2. 구현 편의를 위한 하드코딩보다, 재사용 가능한 부분은 추상화할 것

## 1. 지시 이해 원칙

- 지시가 애매하거나 여러 해석이 가능하면, 바로 구현하지 말고 **어떤 해석으로 진행할지 먼저 짧게 확인**한다.
  - 예: "카드 시스템 좀 고쳐줘" → 어떤 버그/어떤 파일 범위인지 되묻기
- 코드 변경 전, 관련 기존 코드(비슷한 클래스, 인터페이스, 네이밍 규칙)를 먼저 찾아서 **기존 패턴을 따르는 것을 기본값**으로 한다. 새 패턴을 도입해야 한다면 이유를 먼저 설명한다.
- 지시에 없는 범위까지 임의로 확장하거나, 반대로 지시의 일부를 빠뜨리고 "완료했다"고 하지 않는다. 작업 범위가 애매하면 범위를 먼저 제시하고 확인받는다.
- 요청 하나에 여러 단계가 얽혀 있으면, 진행하기 전 단계를 짧게 요약해서 보여준다 (긴 계획 문서 말고 3~5줄 정도).

## 2. 하드코딩 대신 추상화하는 기준

**추상화해야 하는 경우** (지시를 구현하다가 아래에 해당하면, 그냥 하드코딩하지 말고 구조를 잡을 것):
- 같은 종류의 값/로직이 **이미 2곳 이상**에서 반복되거나, 반복될 게 확실한 경우 (예: 카드 룰, 무기 스탯, 업그레이드 옵션 등)
- 매직 넘버/매직 스트링(태그 이름, 위젯 키 등)을 여러 곳에 직접 박아 넣는 경우 → 상수/데이터 테이블/Enum으로 분리
- 이미 프로젝트에 전략 패턴/인터페이스(`PhaseStrategy`, `*Interface.h` 류)로 확장 가능하게 만들어둔 영역에 새 케이스를 추가하는 경우 → 기존 추상화를 따라 확장 지점을 사용
- "나중에 기획이 바뀌면 값만 바꿔서 대응해야 하는" 데이터성 로직 (밸런스 수치, 카드 규칙, 상점 아이템 등)

**추상화하지 않아도 되는 경우** (과설계 방지):
- 지금 당장 한 곳에서만 쓰이고, 확장될지 불확실한 로직
- "혹시 나중에 필요할 수도 있으니" 식의 추측성 확장 포인트
- 이 경우엔 일단 단순하게 구현하고, 필요해지면 그때 리팩토링 대상으로 표시(TODO 아님, 대화 중 언급)

**판단이 애매하면**: 구현 전에 "이 부분은 A처럼 하드코딩할지, B처럼 추상화할지 애매한데 어느 쪽으로 할까?" 라고 먼저 묻는다.

## 3. 프로젝트 컨텍스트 (참고용)
- 언리얼 엔진 C++ 프로젝트, GAS(Gameplay Ability System) 사용
- `PhaseStrategy`, `*Handler`, `*Interface` 네이밍/구조가 이미 확립되어 있음 → 새 기능도 이 구조에 맞출 것
- (필요하면 여기에 폴더 구조, 네이밍 컨벤션, 브랜치 전략 등 추가)

## 4. 작업 완료 보고
- 무엇을 바꿨는지, 왜 그렇게 추상화했는지(또는 안 했는지) 한두 줄로 설명한다.
- 확인 없이 임의로 스코프를 넓혀 리팩토링하지 않는다.

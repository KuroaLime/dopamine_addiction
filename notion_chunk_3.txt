려진 바가 없었다. 막연한 감으로 GPU 설정을 만지기 전에, 실제로 시간이 어디서 쓰이는지부터 측정으로 확인하는 것을 목표로 잡았다.\n\t## 설계 및 구현\n\t### 측정 도구부터 직접 만들어야 했다\n\t기존 프로파일링 도구들이 이 프로젝트의 조건에 그대로 맞지 않았다. Unreal CsvProfiler가 뽑는 CSV는 `FMsgLogf`/`FMsgLogfCount` 같은 중복 컬럼명 때문에 PowerShell의 `Import-Csv`로 파싱하면 실패해서, 필요한 컬럼만 헤더 위치로 직접 찾아 파싱하는 `Analyze-Csv.ps1`을 만들었다. 또한 이 게임은 멀티플레이어 게임모드(`bPauseable=false`)라 에디터 PIE에서 `pause`가 거부되고 `Simulate In Editor`도 게임이 아니라 에디터 자체를 측정해버려서, 시점을 일정하게 유지한 채 반복 측정하기 위한 마우스 시점 자동화 스크립트(`look-driver-safe.py`)도 별도로 만들어야 했다.\n\t### 1차 결론: \"GPU가 무겁다\" — 그리고 정정\n\t에디터 PIE에서 `ProfileGPU`로 잰 첫 측정은 TPS 섬 구간에서 GPU 39.3ms(P90 46.3ms)까지 나와, 자연스럽게 \"GPU 바운드\"라는 결론으로 이어졌다. PostProcessing(TSR 포함) 6.25ms, ShadowDepths(VSM Non-Nanite 4.05ms) 5.90ms 등 GPU 쪽 항목들이 실제로 크게 잡혔기 때문이다.\n\t그런데 이 결론은 틀렸다. Standalone 빌드(`-game`, 1600x900)로 다시 측정하면서 `r.ScreenPercentage`를 100→70→100으로 스윕해봤는데, 해상도를 49%로 줄이면 GPU Time은 14.0ms → 10.6ms(-27%)로 확실히 떨어지는데도 실제 프레임 타임(`Draw`, 렌더 스레드)은 약 16ms에서 전혀 움직이지 않았다:\n\t```javascript\nGPU Time         14.36/14.01 (100%) → 10.67/10.58 (70%) → 14.59/14.48 (100%)\nDraw(렌더스레드)  15.82/16.62 (100%) → 16.03/16.39 (70%) → 16.00/15.94 (100%)\n\t```\n\tGPU를 아무리 깎아도 프레임이 그대로라는 것은 병목이 GPU가 아니라 렌더 스레드라는 뜻이었다. 에디터 PIE에서 GPU가 커 보였던 이유도 뒤늦게 밝혀졌다 — 에디터는 병렬 렌더링 처리 때문에 CSV에 `RenderThreadTime`이 거의 0으로 잡혀서, 렌더 스레드가 실제로 얼마나 쓰이는지 애초에 볼 수 없는 측정 환경이었던 것이다. `stat dumpframe`으로 렌더 스레드 14ms를 뜯어보면 그중 약 4ms는 작업이 아니라 병렬 visibility 워커와 RHI 스레드를 기다리는 CPU 스톨(`CPU Stall - Wait For Event`)이었다.\n\t### 근본 원인: 씬 인스턴스 3,549개 중 3,543개가 Movable\n\t`stat dumpframe -ms=0 -root=initviews`로 인스턴스 구성을 뽑아보자 원인이 드러났다:\n\t```javascript\nNum Dynamic Instances : 3,543\nNum Static Instances  :     1\nScene Instance Count  : 3,549\n\t```\n\t섬을 띄우는 `UFloatingMotionComponent`는 섬 루트의 Mobility를 Movable로 요구하고, 그 아래 붙은 나무·바위·구조물이 전부 이 Mobility를 그대로 상속받는다. 그 결과 씬 전체가 사실상 Movable이 되어 정적 컬링 캐시와 드로우 커맨드 캐싱을 쓸 수 없고, 매 프레임 relevance를 재계산하며, 레이트레이싱 dynamic update primitive 3,730개가 매 프레임 갱신됐다.\n\t다만 \"부유 모션 자체가 무겁다\"는 가설도 A/B/B/A 순서로 뒤집어 검증했는데 — `UFloatingMotionComponent`를 껐다 켜는 순서를 바꿔도 결과가 그대로 따라와서 인과가 없었다. 비용은 \"움직이고 있다\"는 사실이 아니라 \"Mobility가 Movable이다\"라는 타입 자체에서 나오고 있었다.\n\t### 적용한 수정: 로프 브릿지를 Lumen에서 제외\n\t섬과 섬을 잇는 로프 브릿지(`ARopeBridge`)는 섬이 부유할 때마다 매 프레임 다시 빌드되는데(`RebuildBridge()`), 이게 Lumen 서페이스 캐시의 \"메시 카드\"(`CardPageRenderPasses`)를 매 프레임 무효화시키고 있었다. 렌더 스레드에서 5개 다리를 기준으로 A/B/A/B로 측정한 결과는 다음과 같다:\n\t```javascript\n다리를 Lumen에 포함     UpdateLumenScene 2.4-3.5ms, CardPageRenderPasses 2.2-3.3ms\n로프만 제외             UpdateLumenScene 2.4ms,     CardPageRenderPasses 2.2ms   (효과 없음)\n다리 전체를 제외        UpdateLumenScene 0.15ms,    CardPageRenderPasses 사라짐\n\t```\n\t의외였던 부분은 \"로프만 Lumen에서 빼면 효과가 없었다\"는 점이다. Lumen 카드는 표면적에 비례해서 비용이 매겨지는데, 로프는 가늘어서 표면적이 거의 없고 실제 비용은 판자(Plank)와 기둥(Biseok) 쪽에서 나오고 있었다. 그래서 다리를 구성하는 모든 `UPrimitiveComponent`(판자 ISM, 세로 로프 ISM, 기둥 4개)를 한꺼번에 순회하며 제외하는 `ExcludeAllFromLumen()`으로 구현했다:\n\t```c++\nvoid ARopeBridge::ExcludeFromLumen(UPrimitiveComponent* Prim)\n{\n    if (!Prim || (!Prim->bAffectDynamicIndirectLighting && !Prim->bAffectDistanceFieldLighting))\n    {\n        return;\n    }\n\n    Prim->bAffectDynamicIndirectLighting = false;\n    Prim->bAffectDistanceFieldLighting = false;\n    if (Prim->IsRegistered())\n    {\n        Prim->MarkRenderStateDirty();\n    }\n}\n\t```\n\t다리가 트인 공중에 걸쳐 있어 어차피 주변에 반사광(GI)을 거의 기여하지 않는다는 점도 이 최적화를 선택한 근거가 됐다 — 이 플래그를 끄는 것은 다리가 Lumen 전역조명에 \"기여\"하는 것만 막을 뿐, 다리 자체가 빛을 받아 보이는 데는 영향이 없다. 이미 플래그가 꺼져 있으면 곧바로 반환하도록 만들어서, 섬이 부유하며 매 프레임 브릿지를 리빌드해도 이 처리를 반복 호출하는 비용은 무시할 수 있는 수준으로 유지했다.\n\t## 결과\n\t- \"GPU가 무겁다\"는 1차 결론을 실제로는 렌더 스레드가 GPU를 기다리는 스톨이 대부분이었다는 사실로 정정하면서, 에디터 PIE 측정치를 그대로 믿으면 안 되고 Standalone 빌드 + `ScreenPercentage` 스윕처럼 저비용은 아니라는 것을 배움\n\t- 기존 도구가 이 프로젝트의 측정 조건(멀티플레이어라 일시정지 불가, CSV 중복 컬럼명)에 맞지 않아 프로파일링 도구 자체를 직접 만들어야 했던 경험\n\t- 남은 과제: 근본 원인인 \"씬 전체가 Movable\"이라는 문제 자체는 아직 남아 있다. 가장 큰 효과가 기대되는 섬별 정적 장식물의 ISM/HISM 병합은 아직 착수 전이고, 로프 브릿지 Lumen 제외는 그 전에 먼저 잡을 수 있었던 개별 항목에 대한 부분적 완화다.\n</details>\n<details>\n<summary>09 - 카드 배치 실패 진단 로깅</summary>\n\t## 문제/배경\n\tTPS 전투 맵의 섬 위에 카드를 띄울 때는 내비메시 보행 가능, 존(Zone) 경계 내부, 기존 카드와 충분한 거리, 장애물에 가려지지 않음, 머리 위 공간 확보, 진입금지구역이 아닐 것까지 다섯 가지 조건을 모두 만족해야 했다. 이 다섯 가지 검사를 내비메시 기반 배치 경로와 그 폴백인 지면 트레이스 기반 배치 경로가 각각 따로 구현해 두었고, 실패했을 때는 \"실패했다\"는 로그 한 줄뿐 왜 실패했는지는 알 수 없었다.\n\t## 설계 및 구현\n\t### 중복 검사 통합 — ClassifyIslandCandidate\n\t내비메시 경로와 지면 트레이스 폴백 경로가 각자 같은 다섯 가지 검사(Z 범위, 진입금지구역, 거리, 충돌, 머리 위 공간)를 같은 순서로 복사해 놓고 있었다. 검사 하나를 바꾸거나 순서를 바꿀 때 한쪽만 고치고 다른 쪽을 놓치기 쉬운 구조라, 단일 함수 `ClassifyIslandCandidate()`와 거부 사유를 나타내는 `enum class ECardDropReject`로 묶었다:\n\t```c++\nenum class ECardDropReject : uint8\n{\n    Accepted,\n    ZOutOfRange,\n    InsideNoDropZone,\n    TooCloseToOtherCards,\n    Blocked,\n    NoOverheadClearance,\n};\n\nECardDropReject FCardPlacementService::ClassifyIslandCandidate(\n    const FCardIslandDropZone& DropZone,\n    float ReferenceZ,\n    const FVector& Candidate,\n    const TArray<FVector>& ExistingIslandLocations) const\n{\n    if (!IsCardDropZSane(DropZone, ReferenceZ, Candidate))      return ECardDropReject::ZOutOfRange;\n    if (IsInsideNoDropZone(Candidate))                          return ECardDropReject::InsideNoDropZone;\n    if (!IsFarEnoughFromIslandCards(Candidate, ExistingIslandLocations)) return ECardDropReject::TooCloseToOtherCards;\n    if (!IsCardDropLocationClear(Candidate))                    return ECardDropReject::Blocked;\n    if (!HasOverheadClearance(Candidate))                       return ECardDropReject::NoOverheadClearance;\n    return ECardDropReject::Accepted;\n}\n\t```\n\t호출하는 쪽(내비 경로, 지면 트레이스 폴백)은 여전히 자기 흐름(return 할지 continue 할지)과 자기 실패 카운터를 직접 관리하고, `ClassifyIslandCandidate`는 판정 자체만 공용으로 제공하는 형태로 역할을 나눴다.\n\t### 진단 로깅 — 어떤 조건이 가장 많이 막았는지 집계\n\t중복 제거만으로는 \"왜 실패했는지\"가 로그에 드러나지 않는 문제가 남아 있었다. 이를 위해 `PickIslandCardDropLocation`에 `OutFailureReason` 출력 파라미터를 추가하고, 내비 경로/지면 폴백 각각에서 조건별 실패 횟수를 이름 붙은 카운터(`NavProjection`, `Bounds`, `ZRange`, `Distance`, `Collision`, `Overhead`, `NoDropZone`, `GroundTrace`, `Walkability`)로 누적한 뒤, 그중 값이 가장 큰 항목을 \"지배적 실패 사유\"로 뽑아 로그에 남기도록 했다:\n\t```c++\nconst TCHAR* DominantReject = TEXT(\"Unknown\");\nint32 DominantCount = 0;\nconst TPair<const TCHAR*, int32> RejectCounts[] =\n{\n    { TEXT(\"NavProjection\"), NavFail },\n    { TEXT(\"Bounds\"), BoundsFail + GroundBoundsReject },\n    { TEXT(\"ZRange\"), ZFail + GroundZReject },\n    { TEXT(\"Distance\"), DistFail + GroundDistReject },\n    { TEXT(\"Collision\"), OverlapFail + GroundOverlapReject },\n    { TEXT(\"Overhead\"), OverheadFail + GroundOverheadReject },\n    { TEXT(\"NoDropZone\"), NoDropFail + GroundNoDropReject },\n    { TEXT(\"GroundTrace\"), GroundTraceFail },\n    { TEXT(\"Walkability\"), GroundWalkableReject },\n};\nfor (const TPair<const TCHAR*, int32>& RejectCount : RejectCounts)\n{\n    if (RejectCount.Value > DominantCount)\n    {\n        DominantReject = RejectCount.Key;\n        DominantCount = RejectCount.Value;\n    }\n}\nFailureReason = FString::Printf(TEXT(\"AllCandidatesRejectedMostlyBy%s\"), DominantReject);\n\t```\n\t이 값은 최종 실패 로그(`[DS] Card DropFail ... Reason=%s ...`)에 다른 모든 개별 카운터와 함께 그대로 남아서, 로그 한 줄만 보고도 \"이 섬은 후보 대부분이 Z 범위 밖이라 막혔다\"거나 \"대부분 다른 카드와 너무 가까워서 막혔다\" 같은 결론을 바로 낼 수 있게 됐다.\n\t## 결과\n\t- 이 작업은 배치 판정 로직 자체를 바꾼 게 아니라, 같은 판정 결과를 더 잘 진단할 수 있게

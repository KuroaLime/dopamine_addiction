지점을 서버 권위로 관리하면서 클라이언트에도 상태가 동기화되는 시스템이 필요했다.\n\t## 설계 및 구현\n\t`AA_Spawn` 액터에 `bReplicates`, `bAlwaysRelevant`를 설정하고 `DOREPLIFETIME` + `OnRep_BarrierActive`로 점유 상태를 클라이언트에 복제해, `USpawnManagerComponent`(GameMode 소유)가 서버 권위로 전체 스폰 지점을 관리하도록 했다.\n\t최초 구현의 스폰 후보 선택 로직은 단순했다 . 후보 배열에서 무작위 인덱스를 하나 뽑아 반환하면서 그 자리에서 배열에서 제거하는 방식이었다:\n\t```c++\nAA_Spawn* USpawnManagerComponent::GetUniqueRandomSpawnActor() {\n    if (AvailableSpawns.Num() == 0) return nullptr;\n    int32 RandomIndex = FMath::RandRange(0, AvailableSpawns.Num() - 1);\n    AA_Spawn* SelectedSpawn = AvailableSpawns[RandomIndex];\n    AvailableSpawns.RemoveAt(RandomIndex);\n    return SelectedSpawn;\n}\n\t```\n\t문제는 이 방식이 후보를 그대로 \"소모\"한다는 것이었다. “사망→리스폰”이 반복되는 매치 특성상 스폰 지점 개수만큼 뽑히고 나면 후보군이 완전히 고갈되고, 그 이후로는 리스폰 자체가 실패하는 구조적 결함이었다. 이를 고치기 위해 후보를 배열에서 제거하지 않고 커서로 순회하다가, 한 바퀴를 다 돈 커서가 처음으로 돌아왔을 때만 다시 섞는 방식으로 바꿨다:\n\t```c++\nAA_Spawn* USpawnManagerComponent::GetUniqueRandomSpawnActor() {\n    AvailableSpawns.RemoveAll([](const AA_Spawn* SpawnPoint) {\n        return !IsValid(SpawnPoint);\n    });\n\n    if (AvailableSpawns.IsEmpty())\n    {\n        InitializeSpawnPoints();\n        AvailableSpawns.RemoveAll([](const AA_Spawn* SpawnPoint) {\n            return !IsValid(SpawnPoint);\n        });\n    }\n\n    if (AvailableSpawns.IsEmpty()) return nullptr;\n    if (!AvailableSpawns.IsValidIndex(UniqueSpawnCursor)) UniqueSpawnCursor = 0;\n\n    if (UniqueSpawnCursor == 0)\n    {\n        Algo::RandomShuffle(AvailableSpawns);\n    }\n\n    AA_Spawn* Picked = AvailableSpawns[UniqueSpawnCursor];\n    UniqueSpawnCursor = (UniqueSpawnCursor + 1) % AvailableSpawns.Num();\n    return Picked;\n}\n\t```\n\t이 방식으로 라운드가 아무리 반복돼도 후보군이 고갈되지 않으면서, 매번 완전 재셔플할 때보다 체감 분포도 고르게 유지할 수 있었다.\n\t여기에 별개의 문제가 하나 더 있었다. 스폰 지점 마커들이 별도로 스트리밍되는 서브레벨에 배치되어 있어서, `USpawnManagerComponent`가 `BeginPlay`에서 월드를 처음 스캔하는 시점에 그 레벨이 아직 로드되지 않아 후보 배열 자체가 비어버릴 수 있었다. 후보군이 비어 있으면 그 시점에 한 번 더 재스캔하도록 해서 해결했다:\n\t```c++\nif (CenterSpawns.IsEmpty())\n{\n    // The streamed spawn level may not have existed when BeginPlay first scanned the world.\n    InitializeSpawnPoints();\n    CenterSpawns.RemoveAll([](const AA_Spawn* SpawnPoint) {\n        return !IsValid(SpawnPoint);\n    });\n    AvailableSpawns.RemoveAll([](const AA_Spawn* SpawnPoint) {\n        return !IsValid(SpawnPoint);\n    });\n}\n\t```\n\t리스폰 처리 자체도 처음에는 `TeleportTo` 호출 결과를 검사하지 않고 곧바로 성공한 것처럼 다음 로직(HP 복구, 상태 전환)으로 넘어갔다. 텔레포트가 지형이나 다른 오브젝트와 겹쳤을 때 이를 감지할 방법이 없었던 것이다. 이를 서버 권위 하에 목표 좌표를 검증하고 실패 시 재시도하는 구조로 바꿨다. 먼저 목표 좌표에 NaN이 없는지 확인한 뒤 `TeleportTo`를 시도하고, 실패하면 `SetActorLocationAndRotation`으로 한 번 더 시도하며, 최종적으로 적용된 위치가 요청한 위치와 오차 범위 안에 있는지까지 검사한다:\n\t```c++\nconst bool bTeleported = Pawn->TeleportTo(TargetLocation, TargetRotation, false, true);\nbool bApplied = bTeleported;\nif (!bApplied)\n{\n    bApplied = Pawn->SetActorLocationAndRotation(\n        TargetLocation, TargetRotation, false, nullptr, ETeleportType::TeleportPhysics);\n}\n...\nconst float LocationError = FVector::Dist(TargetLocation, Pawn->GetActorLocation());\nconst bool bWithinTolerance = LocationError <= PositionTeleportMaxLocationError && ...;\n\t```\n\t이 검증이 실패하면 리스폰 어빌리티가 그 자리에서 즉시 실패로 끝내는 대신, 1초 간격으로 재시도하도록 만들었다:\n\t```c++\nWorld->GetTimerManager().SetTimer(\n    ServerRespawnRetryTimerHandle, this,\n    &UAbility_Respawn::TryCompleteServerRespawn, 1.f, false);\n\t```\n\tHP 복구와 조작 권한 반환은 이 텔레포트가 검증까지 완전히 성공한 뒤에만 실행되도록 순서를 고정해서, 겹침 상태로 어중간하게 리스폰된 채로 조작이 풀리는 상황을 막았다.\n\t로비 캐릭터 스폰(`Lobby_RoomCharacterSpawner`)에도 같은 커서 방식을 적용해보려 했지만, 실제로 로비가 다루는 문제는 성격이 달랐다 — 방 슬롯마다 고정된 스폰 위치가 있고 룸 멤버 목록도 서버가 이미 슬롯 인덱스와 함께 갖고 있어서, 커서로 순회할 필요 없이 멤버 목록의 인덱스와 스폰 위치를 그대로 매칭하는 결정적(deterministic) 방식으로 처리했다. 카드 라운드 종료 후에는 서버가 모든 PlayerController를 순회하며 권위적으로 재배치하는 것으로 마무리했다.\n\t## 결과\n\t- 후보를 제거하는 소모형 풀은 편중보다 \"고갈로 인한 실패\"가 더 치명적인 문제일 수 있다는 것을 실제로 겪고 체감\n\t- 스트리밍 레벨을 쓰는 프로젝트에서는 `BeginPlay` 시점의 월드 스캔이 항상 성공한다고 가정하면 안 되고, 비어있을 때 재스캔하는 방어 로직이 필요함을 체감\n\t- 위치를 바꾸는 작업(텔레포트)은 호출 성공 여부를 검사하지 않으면 겹침 등으로 실제로는 실패해도 성공한 것처럼 넘어갈 수 있으므로, 결과를 검증하고 실패 시 재시도하는 구조가 필요함을 체감\n\t- 서버 권위 원칙(HasAuthority 가드)을 스폰처럼 사소해 보이는 시스템에도 일관되게 적용해야 치팅/디싱크를 막을 수 있음을 체감\n</details>\n<details>\n<summary>02 - 무기·탄약 네트워크 동기화</summary>\n\t## 문제/배경\n\t탄약 수, 장착 무기, 발사 가능 여부가 서버와 클라이언트 간에 항상 일치해야 했다. 무기 타입별로 소지 탄약을 따로 관리해야 했고, 장착 무기가 바뀔 때 클라이언트 표현(메시 재부착)도 함께 맞춰야 하는 시스템이 필요했다.\n\t## 설계 및 구현\n\t`WeaponComponent`의 `CurrentAmmo`를 `Replicated` 프로퍼티로 선언해 서버 권위 값을 클라이언트에 그대로 복제했다:\n\t```c++\nUPROPERTY(Replicated, BlueprintReadOnly, Category = \"Weapon | Ammo\")\nint32 CurrentAmmo = 30;\n\n// 장전 중 잠금 — true인 동안 사격 불가. 서버에서 set, 복제됨.\nUPROPERTY(Replicated, BlueprintReadOnly, Category = \"Weapon | Reload\")\nbool bIsReloading = false;\n\t```\n\t`bIsReloading`은 처음부터 있던 필드가 아니었다. 재장전 로직은 원래 순수 연출용 Multicast RPC(`Multicast_PlayReloadFeedback`) 안에 탄약 이동이라는 게임플레이 판정과 뒤섞여 있었고, 그 상태에서는 사격 중에도 재장전이 걸릴 수 있는 버그가 있었다. 이를 전용 `Ability_Reload`로 분리하면서 `bIsReloading` 잠금을 추가하고, `Ability_Fire` 쪽에서 재장전 중이면 발사를 막도록 상호 배제시켰다.\n\t문제는 장착 무기가 바뀔 때도 있었다. 탄약 수치는 리플리케이션만으로 자동으로 맞지만, 클라이언트 화면에 실제로 붙어있는 무기 메시는 별도로 다시 붙여줘야 했다. `MainCharacter`의 장착 무기가 바뀌면 `OnRep_EquippedGun`에서 클라이언트가 무기 메시를 소켓에 재부착하도록 처리했다:\n\t```c++\nvoid AMainCharacter::OnRep_EquippedGun()\n{\n\tif
